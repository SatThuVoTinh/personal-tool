## 2. Band A — CI and merge safety (`H1`, `H2`, `H3`)

### A1 — `H1`: the CI trigger widening

`.github/workflows/ci.yml` currently triggers on `pull_request` to `main`,
`push` to `main`, and `workflow_dispatch`. The owner's answer: **turn the
widening on** — a push to the TASK branch must be gated without a human
re-dispatch.

The target shape is the one `security.yml` already uses: a `push` trigger with
**no branch filter** and a `pull_request` trigger with **no branch filter**, so
every branch push and every PR is gated, plus the existing `workflow_dispatch`.

Constraints:

- the `quality-gate` job must stay green on a task-branch push: the Postgres
  service, the Python lane and the Docker-gated suites keep their existing
  behaviour (a suite that needs the container is `NOT RUN` with its compensating
  control, never a silent pass);
- `concurrency` must keep cancelling the superseded run for the same ref;
- the change is a WORKFLOW change only — no job may start writing to a
  protected path or use a secret the workflow did not already have.

### A2 — `H2`: the in-repo merge blocker

GitHub branch protection is not enableable on this plan (`403 "Upgrade to
GitHub Pro or make this repository public"`), and the owner's answer is **(a):
an in-repo merge blocker**. The repository stays private; the gates stay
advisory wherever GitHub cannot enforce them.

The blocker has two halves, and both are honest about what they can do:

1. **A PRE-MERGE check the operator runs** (a script under `scripts/`): it
   refuses to let the operator merge into `main` unless the tip being merged has
   a successful `quality-gate` run at that exact SHA. It reads the run state
   through the GitHub API (`gh run list --commit <sha>`, or `GITHUB_TOKEN`), it
   fails closed when it cannot determine the state, and it prints the run URL.
2. **A POST-MERGE detector on `main`**: a CI job that fails LOUDLY when the
   merged commit has no successful `quality-gate` run at its own SHA — the
   evidence that the merge went in ungated, visible in the run list.

The script refuses rather than warns when the evidence is missing, unknown or
older than the commit. It never edits a branch, never pushes, and never
touches the remote: it is a gate, not an action.

### A3 — `H3`: the per-family skip expectation

CI currently prints green while whole families of tests are skipped. The
owner's answer: **set an expectation**, and the measurement says it must be a
PER-FAMILY expectation, not one global number (a single global number would
fire on ~40 legitimate host-capability skips).

Target shape:

- a DECLARED table of the skip families and the number of skips each family may
  have on the CI runner (the Docker/Postgres family, the duckdb family, the
  WSL-only family, the PDF family, …), each with the reason;
- a gate that reads the run's own test output and compares each family's skip
  count with its declaration, failing when a family skips MORE than declared,
  and failing when a family that is expected to run is skipped entirely;
- the table is derived from the repository's own lane list, not from a second
  hand-written copy of the test names.

The gate never lowers a declared expectation to make a run pass; an expectation
is changed only in the same commit that explains why.

## 3. Band B — the register becomes the open queue (`H10`)

The owner's answer, verbatim in intent: *a bug that is fixed and PROVEN may be
deleted from `findings.md`, and the history goes to `CHANGELOG.md`.*

Target shape:

- `docs/execution/findings.md` holds the OPEN queue: the rows that are still
  open, the rows whose premise was measured dead (`REFUTED`), and the rows
  parked on a decision (`EXCLUDED`). The §2 closure table is removed;
- every closed row's history — its id, its one-line defect, its fix commit and
  its evidence — moves into `CHANGELOG.md` under the `[Unreleased]` section,
  grouped by the band that closed it;
- the register's own preamble (§0.2, the per-bug process) is updated to state
  the new rule and to say where a closed row's history lives;
- `PLAN.md` §4.17 and the cross-references that name a closed row are updated
  so no pointer points at a row that no longer exists.

The rows that are NOT fixed stay where they are: a `REFUTED` row was never
fixed (its premise was dead) and an `EXCLUDED` row is parked, not closed. A row
that this band's own answers RELEASE (`H1`, `H2`, `H3`, `H5`, `H6`, `H8`, `H9`,
`H10`) becomes open work again, with the answer recorded in its `Status` line.

## 4. Band C — the Skill Store (`H5`, `H8`, `H9`)

- **`H5`:** the `skills.*` DDL and the migration runner move into
  `zink-skill-store/`, the module that owns the Skill Store's persistence. The
  Knowledgebase's migration set keeps its own tables. The decision is about DDL
  PLACEMENT only — no data is moved, no applied migration is edited (the
  applied ones are keyed by filename and digest-pinned), and the Skill Store
  keeps its own migration ledger.
- **`H8`:** the Skill Store gains a GOVERNED `DEPRECATED` retirement path: a
  promoted skill can be retired through the governed API (not by editing the
  tree), the state transition is recorded in the durable record, and the change
  lands as a FORWARD migration (a new file), never as an edit of an applied
  one. `REJECTED` keeps its own writer.
- **`H9`:** the derived text copies that cannot be reclaimed get a reclamation
  path: the PDF stays, the derived copy is reclaimed under the store's own
  writer, and the reclamation is recorded. It is a retention decision the owner
  approved; it deletes DERIVED content only, never a source document.

## 5. Band D — the secrets and the identities (`H6`, `H7`)

- **`H6`:** the router API key stops being baked into the generated secrets
  plan and goes through the `secrets.providers` indirection like every other
  secret, so it can be rotated without a re-apply of the whole tree. The
  change is to the SECRET PLAN and the provider configuration — no secret value
  is ever printed, logged or committed, and the preflight keeps refusing a
  plan that drifts from the builder's.
- **`H7`:** an UNKNOWN Discord identity in a durable event is recorded in the
  hashed form `F-049` decided (`[PRINCIPAL:<64-hex>]`), is MARKED as unknown,
  and is SURFACED to the owner — not refused, not silent. The owner's own
  identity keeps its historical handling.

## 6. Band E — the digest-pin re-base (`F-217`)

The frozen digest pin of `lib/discord-forum-tags.mjs` (its historical digest,
its commit, its occurrence count and the "the current build's digest must not
be allowlisted" assertion) is re-based as its own objective: the historical
digest stays admitted, the current build's digest stays OUT of the allowlist,
and the assertion is rewritten so the next legitimate change to that asset is
admittable without editing the freeze.

## 7. Acceptance criteria and gates

Every band closes the way `AGENTS.md` §11 and the register's §0.2 require:

1. the premise is re-verified at HEAD;
2. a RED test (or a documented probe) exists before the fix;
3. one commit per finding, naming the `F-xxx` and the legacy id;
4. the affected gates are re-run and the counts are read from the output;
5. the register is synchronized: a fixed and proven row is DELETED from
   `findings.md` (Band B's rule) and its history is in `CHANGELOG.md`;
6. no assertion, gate or ceiling is weakened to make a run pass.

The band's required gates: `npm run format:check`, `npm run lint`,
`node scripts/repository-check.mjs`, the Node suite, and the Python lane for
the bands that touch `apps/knowledge`.
