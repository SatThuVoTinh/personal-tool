#### 4.2.1 Integrity surface (owner decision 2026-10-24)

These paths are **lead-only**, and no agent brief may change that. A parallel lane
that edits one of them produces an unattributable failure, because the gate that
reads them measures the whole integrated tree rather than the lane:

| Path | Why it is serial |
| ---- | ---------------- |
| `package.json` (the `npm test` enumeration) | one 10 412-character string; a test the list omits never runs |
| `integrations/openclaw/topology/lib/schema.mjs` (`PINNED_SCHEMA_MANIFEST_CHECKSUM`) | the committed contract-manifest expectation |
| `integrations/openclaw/configure.mjs` (both per-mode predecessor lists) | an admission asserts what the live host carries; only the lead measures the host |
| `tests/m10-t2-r3-asset-predecessor.test.mjs`, `tests/m8-t2.10-r13-r7-predecessor-allowlist.test.mjs` | the packaged-entrypoint digests |
| `.github/workflows/ci.yml`, `docs/contracts/**` including `*-digests.json` | they change what blocks a merge |

An agent that touches a packaged asset, a contract JSON or adds a test file does
not fix the consequence itself: it **names the file and the new digest in its
report** and stops. The lead rolls the pin, measures the live runtime with
`sha256sum` through `wsl.exe` with `MSYS_NO_PATHCONV=1` (an absolute POSIX path
without that guard is rewritten and reads as "the host does not carry it"), admits
the displaced digest in BOTH per-mode lists when the host carries it, proves the
admission reproducible from a named commit, and runs the pin-removal probe.

The pin roll ships **in the same commit** as the row that moves it.
`tests/agent-last-F-369.test.mjs` compares packaged bytes with
`git show HEAD:<path>`, so an asset change with an uncommitted pin is red by design
and leaves the range un-bisectable.

The real-database lane is a single shared container
(`docker exec -i <CONTAINER> psql` in `tests/m11-t1-postgres-sql-gate.test.mjs`), so
rows that need it run one at a time; two lanes writing `skills.catalog_index`
concurrently is not evidence for either.

## 5. Per-row protocol

1. Re-verify the premise at HEAD using the row's `Where` locators. If dead,
   write a refutation record with the measurement; no code.
2. Check for a duplicate or a closed predecessor in `CHANGELOG.md`, `PLAN.md`
   and the register. Merge before fixing.
3. Write the red test or deterministic probe first. If no red can be built,
   stop and report; do not guess.
4. Make the smallest fix that satisfies the acceptance criteria.
5. Run the affected gates; read counts from the output, not from exit status.
6. Mutation probe: break the new control, confirm the test goes red, revert.
7. Report the disposition to the lead. The lead deletes the row only when
   `H10`'s conditions hold and records the history in `CHANGELOG.md` and
   `PLAN.md`.
8. Commit one row (or the recorded merge).

LATENT rows follow the same protocol with a fault-injection/probe test. If no
deterministic trigger can be built, the row stays LATENT with a written reason;
it is not closed.

- **`F-450` merged with `F-455` (2026-10-24).** Chosen option: add `type` and
