## F-OC-001 — button-bearing Discord payload sent raw when host SDK resolution fails

**Attempted refutation.** Four candidate refutations were traced and all failed:

1. *"The payload is stripped or the send is refused downstream."* False. `sendNativePayload` initializes `let outboundPayload = payload;` (`integrations/openclaw/lib/discord-native-send.mjs:733`) and replaces it **only** inside `if (bundle)` (`:744-755`). With `buttons.length > 0` (`:735`) and `bundle === null`, `context.payload = outboundPayload` (`:787`) carries the caller's own `channelData.discord.components` straight into `adapter.sendPayload` (`:793-796`). No stripping, containment or refusal exists between `:756` and `:795`.
2. *"The bundle is never null on this branch."* False. `buildNativeComponentBundle` (`:414-417`) returns the null half of `resolveNativeComponentBundle`; `resolveComponentSdk` catches every resolution failure and returns `null` after logging `COMPONENT_SDK_UNAVAILABLE … buttons will answer "This component has expired"` (`:311-328`), and `resolveHostDiscordComponentSdk` throws for a missing/exports-less host SDK (`:279-304`). The same null also covers the build-throw path (`:396-406`).
3. *"Registration still happens anyway."* False — and this is the confirmed half. `registerNativeComponents` runs only `if (bundle)` (`:806-814`), so no host registry entry can ever resolve the transmitted ids, which is exactly what the module's own header states (`:21-38`, "Sending components therefore REQUIRES building them with `buildDiscordComponentMessage` … and registering the result").
4. *"Not production-reachable."* False. The pending-result control sender passes **both** `buttons` and a pre-built component payload: `sendNativePayload({ …, buttons, payload: buildNativeComponentPayload({ text: …, buttons }) })` (`integrations/openclaw/plugins/zink-governance/index.mjs:6636-6645`); `buildNativeComponentPayload` really does emit `channelData.discord.components` (`discord-native-send.mjs:178-190`). The approval card sender has the identical shape (`index.mjs:7255-7268`). So a real governed send carries caller-built components.

**Caller semantics verified.** The result-controls caller wraps the send in `try/catch` and only logs (`index.mjs:6647-6651`); the text result was already recorded `WORKFLOW_RESULT_SURFACED` before the controls attempt (`:6598-6609`). Independently of that, `sendNativePayload` returns only `{ messageId, channelId }` (`:815-818`) — it never surfaces a `COMPONENT_REGISTRATION_OUTCOME` to this caller (the outcome enum exists at `:342-349` and is returned only by `registerPostedNativeComponents`/`registerNativeComponents`). So the caller *cannot* distinguish "controls clickable" from "controls dead", even if it wanted to. This strengthens the row rather than refuting it.

**Distinct from F-399 — confirmed.** `F-399` (`docs/execution/findings.md:603-614`) is the `sendWithinDeadline` late-settlement defect: the awaited send times out, the late promise is detached and its rejection absorbed (`discord-native-send.mjs:579-611`), and registration is unreachable because it follows the awaited send (`:790-814`). F-OC-001 needs no timeout and no late settlement: the send settles normally and the defect is decided at `:733-756`, *before* `sendWithinDeadline` is ever called. Neither implies the other; they share only the registration site. Not a duplicate of `F-502` (unwired atomic publisher, `findings.md:1409-1420`), `F-562` (logical-path predicate, `:1825`), or `F-563` (`discord-result-preview.mjs` output-directory guard, `:1838`). Not WRONG-SITE: the mechanism is in the adapter and the raw-components supply is in the plugin caller, as cited.

**Test-gap half confirmed as stated.** `tests/m12-t1-discord-component-registry.test.mjs:285-307` injects a throwing `resolveSdk`, asserts `receipt.messageId === "msg-live-1"` and `COMPONENT_SDK_UNAVAILABLE` in the log and that no `register` call occurred — it never inspects the captured `send` context payload. The build-throw sibling at `:255-283` has the same omission. Both tests pass while raw components are transmitted, so they give false confidence rather than refuting the row.

**Severity: Medium.** Degraded, not system-failing: the owner-visible result text still arrives (and the approval path's own degrade still leaves the `APPROVE <code>` reply path), but the posted controls are unclickable and the status reported to the owner is misleading. No authorization bypass is evidenced — a click that cannot dispatch cannot approve. Not root-cause: it is not the cause of any other row in this bucket or of F-399.

**red: YES.** Any sound fix changes the adapter's outbound public behavior for every component-bearing caller (8 `sendNativePayload` sites in `index.mjs`: 6636, 7255, 7340, 7649, 8673, 10394, 10542, 10750) and the owner-visible approval/result semantics differ depending on the chosen shape: stripping keeps delivery success (and would leave the approval path recording `WORKFLOW_APPROVAL_SURFACED` for a text-only card, `index.mjs:7272-7289`), while refusing turns it into `ANNOUNCE_DELIVERY_FAILED`/BLOCKED with no SURFACED. The row's own acceptance criteria permits both. Adding a registration-outcome field to `sendNativePayload`'s return is a contract change. Owner must pick refuse-vs-strip and the returned-outcome shape (AGENTS.md §7). Smallest sound option: strip `channelData.discord.components` when `bundle` is null (preserving the module's documented text-only degrade at `:36-38`) and return the outcome, with callers kept on their current semantics.

## F-OC-002 — Excel ZIP readers have no aggregate expanded-byte budget

**ZIP claims verified, not assumed.**

1. **`readZipArchive` lacks an aggregate budget — CONFIRMED.** `integrations/openclaw/lib/artifact-validator.mjs:153-206`: the entry count is taken from the 16-bit EOCD field `buf.readUInt16LE(eocd + 10)` (`:164`) and trusted (`:168`); every declared entry is inflated and retained (`:191-198`), capped only **per entry** by `maxOutputLength: MAX_ARTIFACT_SIZE_BYTES` (25 MiB, `:65`). There is no running total, no entry-count ceiling, no pre-retention budget anywhere in the function. `:166-167,206` accumulates `names` + `contents` and returns them.
2. **Repeated-stream claim CONFIRMED at code level.** The parser reads `localOffset` (`:176`) but never requires offsets to be unique and never compares the local-header name (`:181-189`), so *N* distinct central names may point at one local stream and each gets its own retained buffer. Distinctness of names matters — a duplicate name would overwrite in the `Map` (`:191`), which the row's wording ("distinct names") gets right.
3. **Compressed-input ceiling does not bound retained bytes — CONFIRMED.** `:791-802` bounds `stat.size` before `readFileSync` (`:807`); the ceiling is on archive bytes on disk, not expansion.
4. **`excel-writer` `inflateRawSync` has no `maxOutputLength` — CONFIRMED.** `integrations/openclaw/lib/excel-writer.mjs:170`: `const content = method === 0 ? Buffer.from(raw) : zlib.inflateRawSync(raw);` — no option object at all, retained in `entries` (`:142,171`), looped over the unvalidated 16-bit count (`:140-143`). This sink lacks even the validator's per-entry cap.
5. **Production reachability — validator sink CONFIRMED.** `execution_finished` resolves the governed sandbox and maps event artifact entries onto it (`index.mjs:10061-10071`, `readExecutionArtifacts` `:2779-2804`), `handleExecutionFinished` enforces containment and the pre-read size ceiling and hashes the bytes (`:3033-3082`, `artifactSizeCeilingFailure` `:2915-2933`), then calls `evaluateResultGate` (`:3125-3134`) → `validateTechnicalArtifact` (`artifact-validator.mjs:1664-1667` / `:655`) → excel tier → `readZipArchive(contentBuf)` (`:907`) → `inspectExcelSheetParts` (`:618,926`). A `.xlsx` governed result therefore reaches the parser inside the gateway process. Not an inert schema limit.
6. **Production reachability — writer sink CONFIRMED as a live tool path.** `zink_excel` is a registered callable interface (`integrations/openclaw/lib/policy.mjs:2390-2402`) whose handler calls `executeExcelOperation(params, sandboxDir)` with the resolved agent sandbox (`index.mjs:4845-4863`; `resolveAgentSandboxDir` `:3720-3753`). Inside `executeExcelOperation`, `load` reads the workbook bytes and calls `readWorkbookSheetNames` (`excel-writer.mjs:695` → `:192-193` → `readZipEntries`), `validate` does the same (`:740`), and `populate` reads the model-named template (`:795-823` → `buildPopulatedWorkbook` `:516-517` → `readZipEntries`). So the uncapped inflate is on a governed, tool-callable path, independent of result validation.

**No refutation found.** `F-464` (closed: size bound before read — `CHANGELOG.md:2073-2074`) and `F-465` (closed: per-part `maxOutputLength` + sheet-XML parsing — `CHANGELOG.md:2076-2077`) bound the *compressed input* and the *per-entry* output respectively; neither is an aggregate/entry-count budget, and the `readZipArchive` docblock itself (`:141-148`) only claims the per-part cap. So the row is not refuted by those closures, and it is not a duplicate of them. `F-502` is a different mechanism (`artifact-validator.mjs:1445` publisher, unwired — grep-consistent with the register). `F-562` (`:1405-1407` path tier) and `F-563` (preview output dir) are path-contract items at different sinks. No existing register row covers aggregate ZIP expansion; the grep over `findings.md` for ZIP/inflate/aggregate terms returns only this candidate row plus unrelated aggregates.

**Where the row overstates.** The reproduction's "theoretical aggregate above 1.5 TiB" is arithmetic on the 16-bit count and the 25 MiB per-entry cap, not a measurement, and the central directory itself consumes part of the 25 MiB input bound. The `MemoryMax=768M` cgroup ceiling is real (`integrations/openclaw/lib/policy.mjs:1989`), so the credible outcome is gateway OOM-kill/restart and loss of in-flight governed work (an availability outage), not host-wide memory exhaustion. The row already records this bound at `findings.md:2161`; the headline should be read the same way. Test evidence supports the gap: `tests/m8-t2-governed-runtime-audit.test.mjs:3491,3807,3861` and the structural ZIP cases use small archives and assert no count or expanded-byte cap; nothing in the repo asserts an aggregate budget.

**Severity: High.** Exploitable availability defect on a production-gated code path (crafted or corrupt governed Excel result, or a crafted workbook/template in a specialist sandbox, terminates the OpenClaw gateway). Not root-cause: the shared budget policy is one fix, but no other register row in this bucket is a symptom of it. **Type: F6** per §0.4 (resource exhaustion / reliability), not F2 — no boundary is crossed, the service is taken down.

**red: YES.** The fix introduces resource ceilings where none exist (AGENTS.md §7 "resource ceiling"), and the chosen budgets change accepted-shape behavior for every shared-parser consumer: `readZipArchive`/`inspectZipContains*Entries` also serve the Power BI (`artifact-validator.mjs:522-523`) and DOCX (`:1139-1143`, `:1547-1553`) tiers and the name-only reader (`:131-138`), while a writer-side cap changes what governed `load`/`validate`/`populate` accept (`excel-writer.mjs:688-752,795-827`). Values must be owner-approved and must not be met by weakening the existing 25 MiB ceiling. Smallest sound option: a shared explicit entry-count + aggregate-expanded-bytes budget applied *before* retention in both readers, plus a per-entry `maxOutputLength` on the writer inflate, with ordinary valid workbooks still accepted.

**fixer:** `fix-openclaw-artifact-validation` (owns both `artifact-validator.mjs` and `excel-writer.mjs` per `docs/execution/slices.md:61`).
**files a fix would touch:** `integrations/openclaw/lib/artifact-validator.mjs` (`:153-206`, plus consumer assertions for the Power BI/DOCX tiers) and `integrations/openclaw/lib/excel-writer.mjs` (`:123-175`), with regression fixtures (suggested: extend `tests/m8-t2-governed-runtime-audit.test.mjs` or a new `tests/m12-…-zip-budget.test.mjs`).
**depends_on:** none. **root_cause_of:** none.
**Wave note (parallel safety):** `F-OC-003` (`findings.md:2163-2174`) and `F-562`/`F-502` also land in `artifact-validator.mjs` / `excel-writer.mjs`; same fixer, so these must be sequenced in one wave, not dispatched concurrently.

**Unproven without a crafted-archive/resource probe:** (a) that a single sub-25 MiB archive actually drives the gateway to an OOM kill — the retained-bytes growth is code-proven, the crash is not observed; (b) the real expansion ratio achievable under the compressed-input ceiling for the repeated-stream case; (c) whether CPU-time exhaustion or allocation failure surfaces first, and whether either is caught by the existing `try { … } catch {}` at `artifact-validator.mjs:190-202` (that catch turns an over-limit inflate into a *missing part*, not a refusal, so the validator sink's practical outcome may be `CORRUPT_EXCEL` FAIL rather than outage — an important nuance for the *validator* path, since the per-entry cap already throws there; the aggregate risk is the retained `names`/`contents` growth and the writer path's uncapped inflate); (d) how crafted workbook bytes get into the `excel` agent sandbox for the writer sink — no model-callable path to place arbitrary pre-existing bytes there was established in this lane, so that sink is code-confirmed but exploit-setup-unproven (the same qualification `p2/xcheck-oc-artifact.md:40` records for F-OC-003). Register §0.2 still requires a red test or probe before any fix.
