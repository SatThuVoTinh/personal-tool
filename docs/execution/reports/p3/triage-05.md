## F-SKILL-001 — promotion cleanup can follow a linked namespace/capability ancestor

**Verdict: CONFIRMED-AS-LATENT.** The unsafe code path is present and production-reachable, but firing requires a symlink already present as an identity ancestor under the store root. The report does not establish who can plant such a link in a deployment.

- **Refutation attempt — scan order:** A first possible refutation is that `scanCatalog` rejects the link before cleanup. It does not. `promoteApprovedSkillUnlocked` validates only the namespace/capability/version grammar (`zink-skill-store/src/catalog.mjs:1640-1657`), constructs `parentDir` (`:1719-1723`), and calls `healWriterResidue` at `:1733`; the catalog scan is later at `:1843-1844`. In `healWriterResidue`, `readdir(parentDir)` at `:1331-1334` follows symlinks in any ancestor component. If `skills/ns/cap` traverses a symlink to an external directory, its entries are read there; a matching `.pending-*` or `.stranded-*` entry passes `isResidueDirectory` (`:1077-1083`) and `rm(path.join(parentDir, entry), { recursive: true, force: true })` at `:1335-1341` recursively deletes that external child. This is a matching directory inside the symlink target, not recursive traversal through a symlink at the final child.
- **Walk refusal correction:** The Phase 1 locator `walk:689-712` is not the check that fires for this shape. At the root, the loop rejects a linked namespace entry at `:728-739` without descending; one level below, it rejects a linked intermediate/capability entry at `:800-808` and continues. Thus the later walk refuses the catalog, but only after the writer's pre-scan cleanup. `scanCatalog` does reject a linked skills root at `:868-878`; that does not reject an internal linked ancestor.
- **Reachability/callers:** The trusted promotion is called through the public door, which requires the writer lock then delegates to `promoteApprovedSkillUnlocked` (`zink-skill-store/index.mjs:61-70`). Governance loads that door at `integrations/openclaw/plugins/zink-governance/index.mjs:1416-1427`, takes the writer lock at `:1444`, and invokes promotion with the approved stored namespace at `:1451-1465`. No out-of-band/helper-only assumption is needed.
- **Quarantine sibling:** `quarantineInvalidVersion` validates identity strings but builds `versionDir` and `parentDir` from the caller's root/identity at `zink-skill-store/src/catalog.mjs:1452-1479`. Its `lstat(versionDir)` at `:1480-1497` rejects a symlink at the final version component but follows linked ancestors. It then reads/validates the target (`:1498-1509`) and renames it under the linked `parentDir` (`:1510-1514`). For an invalid external pair, this can rename the external directory into the external parent's stranded name. A fix confined to promotion's `healWriterResidue` would leave this same ancestor-confinement defect in the operator repair.
- **Tests/counterevidence:** `tests/m6-t1-skill-store.test.mjs:390-403,557-634` proves catalog refusal for symlinked entries/root, not cleanup-before-scan. `tests/agent-skill-F-580.test.mjs:118-220,283-314` covers a canonical invalid pair and promotion rollback/quarantine behavior, but does not place an outside residue under a symlinked identity path. This aligns with `docs/execution/reports/p2/xcheck-tests-all.md:104-116`. The green post-walk refusal tests therefore do not falsify the pre-scan side effect.
- **Duplicate check:** Not `DUPLICATE-OF F-580` (`findings.md:1955-1966`): F-580 concerns stranding a complete invalid canonical pair and its quarantine/recovery; this finding concerns cleanup/rename escaping through an ancestor symlink. The shared quarantine function is the reason to cover both entry points in this row, not evidence that their causes are duplicates. Not `DUPLICATE-OF F-410`: its closed record (`CHANGELOG.md:2152-2153`) covers writer-created temp residue, exact temp-name recognition and cleanup behavior, not linked-ancestor containment. F-435 (`findings.md:941-952`) concerns promotion export/lock contracts, not path resolution. No other assigned cross-reference is relevant to this mechanism.
- **Type/severity:** `security`; F2. Medium because the unsafe cleanup is code-proven but depends on a pre-existing symlinked identity ancestor; if triggered, it can delete unrelated bytes below a matching residue directory outside `skillsRoot`. Not a root cause for another registered finding.
- **RED:** **YES** — a sound repair enforces filesystem ownership/confinement for canonical promotion and operator quarantine, which is a security boundary under `AGENTS.md` §7. The intended containment is the existing Skill Store root; do not widen the cleanup target.
- **Fixer/files:** `fix-skill-store`: `zink-skill-store/src/catalog.mjs`. `fix-tests`: add a focused regression, preferably `tests/agent-skill-F-SKILL-001.test.mjs`, exercising both promotion and `quarantineInvalidVersion` with an external sentinel beneath a symlinked namespace or capability ancestor. Existing tests may be extended instead, but they must assert the outside bytes and paths remain unchanged.

## F-SKILL-002 — raw alias namespace is stored while scoped search canonicalizes it

**Verdict: CONFIRMED.** The registered proposal route can admit `supply-chain`; the durable proposal and owner approval preserve that spelling; sync writes it into the derived row, while both alias and canonical scoped search spellings become `lscm` in the SQL predicate. Static trace proves the mismatch; PostgreSQL execution was not run.

- **Refutation attempt — admission:** A possible refutation is that `supply-chain` cannot be produced by any shipped writer. It can. The proposal adapter's `VETTED_ROOT_NAMESPACES` includes all alias-map keys (`zink-tools/adapters/skill-store/skill-adapter.mjs:83-95`); the proposal path accepts `namespace` as a string and wraps it as a one-element array (`:1110-1114`), checks the root against that set (`:1116-1123`), and persists `parsedNamespace` unchanged in the durable proposal (`:1151-1176`). `supply-chain` is explicitly mapped to `lscm` (`zink-tools/common/semantic-contract.mjs:36-44`) and included in the governed tool namespace catalog (`integrations/openclaw/lib/policy.mjs:581-626`). The registered proposal tool requires a namespace but does not prohibit this alias (`integrations/openclaw/plugins/zink-governance/index.mjs:4603-4643`); its execution forwards the input as `action: "propose"` (`:4680-4706`). Owner approval compares the stored namespace exactly (`:1312-1324`) and passes it to the trusted promotion (`:1444-1465`). This is a shipped owner-governed route, not a caller bypass.
- **Refutation attempt — storage:** A possible refutation is that semantic metadata derivation also canonicalizes the persisted namespace. It does not. Sync reads the manifest identity namespace (`zink-skill-store/src/vector-sync.mjs:1184-1199`), derives metadata separately (`:1216-1220`), then passes the original `namespace` to `buildSkillSyncTransaction` (`:1307-1321`). The transaction escapes and inserts that supplied value into `skills.catalog_index.namespace` (`:565-576,622-627`). For the admitted identity `['supply-chain']`, the row therefore carries `['supply-chain']`.
- **Refutation attempt — query:** A possible refutation is that alias queries retain the raw spelling or search both spellings. `prepareQueryEmbedding` calls `resolveNamespace` on the alias and sets `metadataFilters.namespace` to the resolved value (`zink-tools/common/semantic-contract.mjs:477-487`); `resolveNamespace` maps `supply-chain` to `lscm` (`:203-210`). The adapter validates the resolved namespace and emits `c.namespace @> <canonical array>` (`zink-tools/adapters/skill-store/skill-adapter.mjs:720-752`). An `lscm` query likewise emits `['lscm']`; neither predicate matches the stored `['supply-chain']` row. The registered `zink_skill_search` passes requests into this adapter (`integrations/openclaw/plugins/zink-governance/index.mjs:4394-4488`) and requires a `namespace` parameter (`:4412-4418`), so the model-facing path has no unscoped fallback for this skill.
- **Other arms/test check:** `discover` compares stored namespace strings directly (`zink-tools/adapters/skill-store/skill-adapter.mjs:462-475`), so canonical `lscm` discovery also misses an alias-stored row. `read`/`apply` use canonical alias binding (`:256-280,649-653`), demonstrating the adapter's own inconsistent identity treatment. Existing alias tests do not refute the SQL mismatch: `tests/m8-t1-skill-vector-memory.test.mjs:1031-1075` checks metadata resolution; `tests/zink-tools-skill-namespace-binding.test.mjs:183-216` checks `power-bi`/`bi` read authorization; and `tests/m11-t1-skill-vector-sql.test.mjs:135-148,167-227` captures SQL for `office`, not alias-backed storage/search. `docs/execution/reports/p2/xcheck-tests-all.md:118-130` identifies the same coverage gap.
- **Duplicate check:** Not `DUPLICATE-OF F-015` (`findings.md:135-146`), which is explicitly REFUTED and about capability casing, rejected by catalog slug validation. Not `DUPLICATE-OF F-434` (`:928-939`), which is row freshness, or `F-572` (`:1890-1901`), which is stored embedding model identity. Not `F-435` (`:941-952`), which is the promotion lock/export contract. Those mechanisms do not canonicalize or compare namespace aliases. No duplicate found.
- **Type/severity:** `contract-mismatch` is the closest allowed fallback type because the durable identity and query scope use incompatible representations; Category F1 is the register's logic/functional classification. Medium: scoped search/discover return false negatives for approved aliases, while no cross-namespace disclosure, data deletion or component outage is evidenced. Not a root cause for another registered finding.
- **RED:** **NO** for the smallest sound repair: preserve raw canonical manifest/DB identity and make the Tools query predicate match the alias and its canonical equivalent, consistent with existing alias semantics in `read`/`apply`. This does not require changing schema, persistence/tombstone identity, public input/output shape, or module ownership. Canonicalizing stored rows instead would alter derived persistence and tombstone semantics and would be RED; it is unnecessary for this repair.
- **Fixer/files:** `fix-tools`: `zink-tools/adapters/skill-store/skill-adapter.mjs` for the query predicate (and exact-string `discover` comparison if kept within this same namespace-consistency defect). `fix-tests`: add/extend a regression, preferably `tests/m12-t9-r4-skill-alias-search.test.mjs`, to capture the SQL generated for a stored `['supply-chain']` identity and verify both alias and canonical scopes match it. No Skill Store writer change is required for the recommended path.
- **depends_on:** none. **root_cause_of:** none.
