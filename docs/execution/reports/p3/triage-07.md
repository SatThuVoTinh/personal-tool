## F-OC-003 — Excel dangling-symlink escape

- **Verdict:** CONFIRMED-AS-LATENT.
- **Type / severity:** F2 — Security & Authorization; Medium. The write escapes the sandbox if the required link exists, but setup is environmental/pre-existing and no model-callable path was found that creates it. The model can select the admitted `file_path` once the link exists. This is a conditional security-boundary failure, not an evidenced model-created exploit chain.

The Phase 1 report gives the concrete generated-workbook path, and both Phase 2 artifact and test cross-checks confirm the sink while explicitly qualifying symlink setup. A repo search of `integrations/openclaw/` found no symlink-creation operation. The governed tool supplies `resolveAgentSandboxDir("excel")` as its base (`integrations/openclaw/plugins/zink-governance/index.mjs:4845-4864`); the Excel contract admits model-supplied `file_path` (`zink-tools/contracts/tools/zink-excel.schema.json:45-53`).
- **Exact evidence:** `integrations/openclaw/lib/excel-writer.mjs:454-467` catches failed `realpathSync`, walks to an existing ancestor and appends unresolved segments; `:474-480` compares the reconstructed target and base; `:660-673` applies that containment to the governed write target; `:841-842` writes through the target path, following a dangling final-component symlink. The concrete condition is an in-sandbox `report.xlsx` symlink to a nonexistent file under an existing outside directory. `docs/execution/reports/p1/scan-oc-2.md:22-32` traces this route. `docs/execution/reports/p2/xcheck-oc-artifact.md:32-43` confirms the static sink but says no model-call path to create the link was established; `docs/execution/reports/p2/xcheck-tests-all.md:160-172` confirms current tests cover junctions/traversal but not this dangling final link. `tests/agent-lib-F-044.test.mjs:39-92` indeed creates a directory junction, not a dangling file symlink. `docs/execution/reports/p2/xcheck-tools-oc.md:41` and `findings.md:1838-1849` establish F-563 as a distinct preview-renderer sink, not a duplicate.
- **Severity rationale:** Medium for a conditional sandbox write-boundary escape with a reachable writer and model-chosen target name, but requiring a pre-existing symlink not shown creatable through the model surface. F-563 is not a reason to lower or merge this finding; its sink and root differ.

## F-OC-004 — release deletes a replacement lock holder

- **Verdict:** CONFIRMED.
- **Type / severity:** F3 — State & Lifecycle Integrity; High. A successful owner check is followed by unlink/rmdir of whatever now occupies the shared directory. If a live replacement holder is erased, another writer can enter the same critical section, threatening authoritative ledgers and queue/decision state.
- **Refutation attempt and result:** The same-path replacement interleaving was traced through both release implementations, callers and coverage. The existing test does not refute it: it replaces B's lock before A validates, so A correctly refuses; it never replaces the lock after A's successful check. The register's exact interleaving remains possible from the code. No runtime race was executed.
- **Exact evidence:** `integrations/openclaw/lib/file-lock.mjs:188-212` reads and compares the current `owner.json` token once. `:220-240` unlinks the current `owner.json` then removes the directory without comparing its token. Sync `release()` checks then calls `removalRound()` at `:264-270`; async `releaseAsync()` does the same at `:294-300` (and does not repeat ownership validation on retries). The shared lock protects DecisionLedger (`integrations/openclaw/lib/decision-ledger.mjs:436-450`), queue operations (`integrations/openclaw/lib/queue-manager.mjs:238-259,375-394`), and topology ledger writes (`integrations/openclaw/topology/lib/ledger.mjs:1503-1508`); Skill Store uses the same module for promotion locking (`zink-skill-store/src/catalog.mjs:16-29`). `docs/execution/reports/p1/scan-oc-3.md:11-21` and `docs/execution/reports/p2/xcheck-oc-gov-topo.md:27-33` independently trace this and identify the shared callers and packaging effect. `tests/m10-t2-r18-file-lock.test.mjs:197-222` only verifies replacement-before-validation; `tests/m11-t3-durable-state-integrity.test.mjs:95-170` checks async release behavior without replacement.
- **Module comments:** `file-lock.mjs:115-120` directly acknowledges the exact replacement-holder scenario: operator removes a live lock, B takes the same path, then A's `finally` must not delete B's lock. That comment supports the risk; it does not implement compare-at-removal. The stale-token comment at `:279-285` acknowledges a related failure mode after exhausted release retries, but its claim that the exhausted token remains registered is contradicted by the immediately preceding current code at `:271-273` and `:283-284`, which deletes both token entries on success and exhaustion. This stale-comment discrepancy does not refute the separate check-then-unlink gap, which occurs after a successful ownership check and before removal.
- **Duplicates / related rows:** Not `DUPLICATE-OF` F-433: that row is the distinct operator recovery-driver removal site (`docs/execution/findings.md:915-926`), while this is the shared lock's release path. F-417 is committed-write error policy (`CHANGELOG.md:2292-2293`), not lock ownership/removal. F-525 is a test skip-idiom defect (`CHANGELOG.md:2289-2290`), not lock behavior. Neither is a duplicate. The Phase 2 report independently says F-433 is analogous but distinct (`xcheck-oc-gov-topo.md:32`).
- **Severity rationale:** High because loss of mutual exclusion can admit concurrent writes to shared authoritative state and cause data-integrity failure. Trigger requires external lock-directory replacement in the narrow post-check window; this limits attack reachability, but does not reduce the potential impact. The caller paths are present.
- **root_cause_of:** none.
- **depends_on:** none.
- **RED:** YES — `file-lock.mjs` defines a shared lock protocol that is an integrity control; changing compare/removal semantics crosses AGENTS.md §7's security/integrity boundary. Preserve sync/async behavior and all shared callers.
