## Cross-check verdicts

### F-KB-001 — oversized PDF sidecar omission

- **Boundary verdict:** Distinct Knowledgebase-only data-loss candidate; no shared Knowledgebase/Skill Store mechanism found.
- **Evidence:** `apps/knowledge/app/pdf_foundation.py:255-263` skips an oversized sidecar without returning its PDF path. `apps/knowledge/app/index_lifecycle.py:206-219,418-435` builds the Knowledge manifest and passes existing paths absent from it as stale; `apps/knowledge/app/database.py:2202-2211` deletes those rows from `knowledge.sources`. The lifecycle evidence and cascade are also recorded in `docs/execution/findings.md:2059-2070`.
- **Shared-state check:** The deletion targets `knowledge.sources`; Skill Store owns `skills.*` and its own migration runner (`docs/contracts/skill-store/agent-skill-store.md:43-52`). No Skill Store caller or state is on this path.
- **Fix blast radius:** Changes to `pdf_foundation.py` or the Knowledge index manifest/publication path affect Knowledge ingestion and `knowledge.*` only. Preserve the existing rule that a failed/uncertain scan does not publish stale-source deletions. A shared deletion or index helper would need to retain owner-specific table and transaction boundaries; no such helper is evidenced here.

### F-KB-002 — applied ALTER migration replay with a missing ledger row

- **Boundary verdict:** Distinct Knowledgebase startup candidate; related to the migration crash window widened under live F-431, but not fully duplicated by it.
- **Evidence:** `apps/knowledge/app/database.py:2790-2819` replays any migration with no `knowledge.schema_migrations` row. `_MIGRATION_OBJECT_PATTERN` at `:137-155` recognizes CREATE forms, while `_migration_is_already_applied` rejects an empty object set at `:2888-2897`. The registered 004/005 migrations are ALTER ADD COLUMN (`docs/execution/findings.md:2072-2083`). Knowledge writes its own ledger at `database.py:2765-2769,2816-2819`; Skill Store declares `skills.schema_migrations` in its own runner (`zink-skill-store/src/migrations.mjs:68-92`).
- **Relationship to F-431:** F-431's register text identifies the DDL/ledger crash interval in both runners (`docs/execution/findings.md:889-900`), so making a migration's DDL and ledger insertion atomic would remove that particular way of creating a missing row. F-KB-002 also reproduces after a row is absent for another reason, such as an excluded/repaired ledger or renamed file (the Knowledge runner itself documents these cases at `database.py:2801-2804`); its CREATE-only replay verifier still cannot recognize an already-applied ALTER. Keep the replay-shape defect distinct, while consolidating the shared crash-window explanation with F-431. The Skill Store runner currently places DDL and its ledger write in one transaction with `ON CONFLICT` (`zink-skill-store/src/migrations.mjs:246-265`), so a Knowledge replay fix must not pull Skill Store migrations back under Knowledge ownership.
- **Fix blast radius:** A change at `apps/knowledge/app/database.py:2797-2819,2874-2901` affects Knowledge startup and its ledger. If a common replay helper is introduced, both migration owners and their different schema/object verification rules become affected; do not let Knowledge inspect or repair `skills.schema_migrations` or apply `skills.*` DDL.

### F-KB-003 — NFC path collision

- **Boundary verdict:** Knowledgebase-only collision candidate and a consequence of the live F-576 normalization behavior; not a Skill Store index collision.
- **Evidence:** `apps/knowledge/app/index_lifecycle.py:210-219` maps every discovered Knowledge source by normalized path. `apps/knowledge/app/database.py:1995-2006` normalizes each source path and deletes an existing row whose `normalize(source_path, NFC)` equals the new key before insertion; `apps/knowledge/migrations/001_initial.sql:81` makes `(index_id, source_path)` unique. The collision case is not exercised by the one-path NFC test cited in `docs/execution/findings.md:2085-2096`. F-576 is the live read-prefix versus writer-form mismatch at `docs/execution/findings.md:1903-1914`; normalizing the writer fixed that mismatch while making two distinct filesystem names share one KB key.
- **Shared-state check:** The implicated key, delete, and unique constraint belong to `knowledge.*`; Skill Store identity uses namespace/capability/version and `skills.catalog_index` (`zink-skill-store/migrations/003_skills_vector_schema.sql:9-25`).
- **Fix blast radius:** A collision guard or identity change at the Knowledge scanner, manifest, writer, or schema affects Knowledge source identity and retrieval. Changing normalization in a shared utility, if one is proposed, could change Tools or Skill Store callers; the current `normalize_source_path` is Knowledge-local (`apps/knowledge/app/database.py:32-41`), and Skill Store does not use Knowledge source paths. Do not change Skill Store keys to compensate for a Knowledge collision.

### F-KB-004 — chunk/citation serializers omit status and ordinal

- **Boundary verdict:** Knowledge API boundary gap with a Zink Tools consumer impact; possible incomplete closure of F-573, rather than shared Knowledgebase/Skill Store state.
- **Evidence:** `apps/knowledge/app/database.py:1905-1925,1961-1967` reads and returns `index_status` and `chunk_ordinal`. The `/v1/chunk` and `/v1/citation` serializers omit them at `apps/knowledge/app/main.py:958-977,998-1025`. F-573's closeout says these loader fields let “a caller” distinguish superseded results and re-derive segment identity (`CHANGELOG.md:2160-2161`), but the HTTP serializers still withhold them. The Knowledge adapter routes retrieve/citation requests to those endpoints (`zink-tools/adapters/knowledge/knowledge-adapter.mjs:405-418`) and its result mapping has no `index_status` or `chunk_ordinal` fields (`:780-821`); the closed tool schema rejects undeclared fields (`zink-tools/contracts/tools/zink-knowledge.schema.json:88-118`).
- **Fix blast radius:** Adding fields at the Knowledge serializers affects the public Knowledge response contract and the Zink Tools Knowledge adapter/schema and their consumers. A safe end-to-end change needs all three to agree. It does not require Skill Store changes. Ask triage to resolve whether the API gap widens/reopens F-573 or becomes a distinct candidate; the loader work and serializer omission are different sites.

### F-SKILL-001 — residue cleanup follows a symlink

- **Boundary verdict:** Skill Store filesystem-ownership violation is supported; no direct Knowledge index/table mutation is shown. The target is outside `skillsRoot`, so its possible filesystem blast radius depends on what the symlink targets.
- **Evidence:** `zink-skill-store/src/catalog.mjs:1723-1733` invokes `healWriterResidue` before the scan. The cleanup enumerates and recursively removes matching entries at `:1331-1341`; the later catalog walk rejects symlink directories at `:689-710`. The residue grammar is the version plus `.pending-` or `.stranded-` (`catalog.mjs:1077-1083`), and the Phase 1 candidate traces the external deletion at `docs/execution/findings.md:2111-2122`.
- **Cross-boundary limit:** Because the cleanup follows a caller-controlled root path and recursively removes matching child directories, a symlink target can be any external filesystem location. No evidence establishes that the target is the Knowledge Vault or another Knowledge-owned path, so do not claim actual Knowledge data loss. The invariant remains that Skill Store cleanup must be confined to validated Skill Store paths; Knowledge ingestion uses its own configured, read-only Vault mount (`infrastructure/docker/compose/compose.knowledge.yml:10-15`).
- **Fix blast radius:** Path validation and cleanup-order changes at `catalog.mjs:1331-1341,1723-1733` affect Skill Store promotion and residue recovery. If a fix changes the shared file-lock implementation, it also affects its other OpenClaw/Tools-hosted callers (`zink-skill-store/src/catalog.mjs:16-29`; `integrations/openclaw/lib/file-lock.mjs:359-405`). No Knowledge source/index change is required.

### F-SKILL-002 — namespace alias write/read mismatch

- **Boundary verdict:** The Phase 1 evidence supports a Skill Store writer / Zink Tools query mismatch. It is not a shared Knowledgebase/Skill Store index defect and should retain its Tools routing.
- **Evidence:** Skill catalog admission permits lowercase slug namespaces without alias resolution (`zink-skill-store/src/catalog.mjs:335-362`). Sync derives semantic metadata from the namespace but writes the original namespace array (`zink-skill-store/src/vector-sync.mjs:575-576,1216-1220,622-627`). Tools resolves `supply-chain` to `lscm` in its shared alias map (`zink-tools/common/semantic-contract.mjs:36-44,203-210`) and uses the resolved namespace in the Skill query predicate (`zink-tools/adapters/skill-store/skill-adapter.mjs:720-751`). Knowledge has its own topic map in `apps/knowledge/app/markdown_adapter.py:62-84` and query normalization in `apps/knowledge/app/retrieval.py:148-202`; both `supply-chain` and `lscm` map to the Knowledge topic “Supply Chain”.
- **Relationship to live findings:** F-015 is REFUTED and concerns capability casing (`docs/execution/findings.md:135-146`); F-434 is table-wide Skill freshness (`:928-939`); neither is this alias persistence mismatch. The namespace-alias fix should be coordinated with the Skill Store writer and Tools query contract, not folded into Knowledge's independent topic mapper.
- **Fix blast radius:** Canonicalizing on write changes derived `skills.catalog_index.namespace` and requires Skill Store sync/migration/reindex consideration plus Tools query alignment. Changing the common alias resolver affects Skill Store vector sync and Tools filtering. Rejecting aliases at Skill Store admission changes accepted canonical skill identities. None of these repairs requires writing to or migrating `knowledge.*`.

## Shared ownership and operational boundary

- **Schema/index ownership is separated in code and contracts.** Knowledge startup creates and migrates `knowledge.*` (`apps/knowledge/app/database.py:2765-2819`). Skill Store owns `skills.schema_migrations` and creates its own schema (`zink-skill-store/src/migrations.mjs:68-92`); its vector writes target `skills.catalog_index`/`skills.segments` (`zink-skill-store/src/vector-sync.mjs:622-667`; `zink-skill-store/migrations/003_skills_vector_schema.sql:9-39`). The Knowledge/Skill contract explicitly prohibits Knowledge startup from mutating `skills.*` (`docs/contracts/skill-store/agent-skill-store.md:43-52`). The indexes have separate tables and HNSW definitions (`apps/knowledge/migrations/001_initial.sql:24-43`; `zink-skill-store/migrations/003_skills_vector_schema.sql:27-39`); shared vector dimension/model conventions do not make the indexes shared mutable state. F-572 remains a distinct Skill row model-provenance gap, not evidence of a shared index (`docs/execution/findings.md:1890-1901`).
- **Shared database credential is the concrete isolation exception and is already routed.** Compose runs Knowledge against database `postgres` as user `postgres` (`infrastructure/docker/compose/compose.core.yml:13-18,145-153`); Skill Store's query executor also invokes `psql -U postgres -d postgres` (`zink-skill-store/src/vector-sync.mjs:307-335`). This is the same cluster-superuser access mechanism identified by F-INFRA-002 and the independent `docs/execution/reports/p2/xcheck-db-all.md:11-23,77-83`. Treat it as one shared privilege-boundary cause; do not create a duplicate finding here. The module runners' separate schemas do not provide database-role isolation while both clients use `postgres`.
- **Runtime sharing and health:** Compose gives the database one persistent `postgres-data` volume and the `platform` network (`infrastructure/docker/compose/compose.core.yml:10-32,216-226`). Knowledge waits for PostgreSQL health (`:145-147`). Skill Store is not a Compose service in the inspected definitions; its sync uses Docker exec against the configured/default PostgreSQL container (`vector-sync.mjs:312-335`). This is a shared infrastructure dependency, but no additional startup-order or health defect was established in this cross-check.
- **Backup coverage:** Generic backup defaults to dumping both `n8n` and `postgres` (`infrastructure/docker/scripts/backup.ps1:7-13`) and dumps each selected database (`:100-110`), so the `postgres` archive contains both logical schemas. Skill Store canonical `skills/` files are Git-native, while PostgreSQL vectors are derived (`docs/architecture/system-overview.md:23-27`; `docs/contracts/skill-store/agent-skill-store.md:15-25,43-52`). The Knowledge recovery drill is explicitly Knowledge-scoped; it is not a claim to restore Skill Store (`docs/execution/reports/p2/xcheck-db-all.md:69-75`). No cross-module backup omission is evidenced here.
- **Tools remains the contract boundary.** The Knowledge API gap has a Tools consumer/schema blast radius, and F-SKILL-002 spans Skill Store and Tools. Do not let either adapter become a direct writer of the other module's indexes; this matches `docs/architecture/platform-boundaries.md:3-23`.
