## Confirmed candidate — unregistered controls on SDK failure

### F-OC-001 — SDK-unavailable pending-result controls are transmitted raw

- **Verdict:** Confirmed and distinct from F-399. The mechanism is SDK/component-bundle resolution failure; F-399 is a late adapter send whose message ID is abandoned after timeout. Neither implies the other.
- **Evidence:** `integrations/openclaw/lib/discord-native-send.mjs:730-756` initializes `outboundPayload = payload`; when `buildNativeComponentBundle()` returns null, no replacement/stripping occurs. The send uses that payload at `:779-795`; registration runs only when a bundle exists at `:805-814`. `resolveComponentSdk()` logs and returns null for an SDK resolution failure at `:311-328`. The production pending-result control sender passes both `buttons` and `buildNativeComponentPayload(...)` at `integrations/openclaw/plugins/zink-governance/index.mjs:6636-6645`. Its caller catches delivery errors and logs but does not inspect a registration outcome at `:6647-6651`. The host registry requirement and the expired-button consequence are documented in the adapter at `discord-native-send.mjs:21-38`.
- **Reachability/impact:** When the SDK cannot resolve (or host component construction fails), a pending-result controls message can still be sent with caller-built raw components. The user sees controls that cannot dispatch through the host registry. This is a dead UI/control availability and truthful-status defect; the text result surface remains, and the register does not establish an authorization bypass from the unregistered controls.
- **Distinct-mechanism check:** F-399 at `docs/execution/findings.md:603-614` covers `sendWithinDeadline` timing out, absorbing a late rejection/resolution and losing a subsequently returned message ID. Here the awaited send itself succeeds with SDK resolution having failed before send; no late settlement is needed. F-OC-001 is a valid new candidate unless Phase 3 consolidates on a broader delivery invariant while preserving both triggers.
- **Fix blast radius:** Primary owner is the native Discord adapter `integrations/openclaw/lib/discord-native-send.mjs:730-814`; direct consumer blast radius includes every governance plugin caller that passes both a component payload and `buttons`, including approval delivery at `index.mjs:7255-7267` and pending-result controls at `:6636-6645`. Any fix that strips controls must preserve visible text and each caller's explicit response semantics: approval delivery currently treats send failure as BLOCKED and writes no SURFACED record (`index.mjs:7272-7278`), while the result has already recorded `WORKFLOW_RESULT_SURFACED` before attempting controls (`:6598-6609`) and logs control failure (`:6647-6651`). The latter can leave a pending result with a surfaced text thread but no button controls. Tests/callers must distinguish adapter result-delivery success from control-registration success. No other logical Zink module should gain component-registry or Discord policy ownership.
- **Coverage note:** `tests/m12-t1-discord-component-registry.test.mjs:285-307` injects SDK unavailability, checks the warning and no registry write, but does not assert the captured send payload is text-only; the build-failure case at `:255-282` likewise omits a payload-component assertion. This is evidence of missing coverage for the unsafe payload branch, not an additional defect.
- **Source candidate:** `docs/execution/findings.md:2137-2148`; scanner evidence `docs/execution/reports/p1/scan-oc-1.md:21-29`.
