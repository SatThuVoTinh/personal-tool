- **Mode:** Audit (Phase 2)

- **Target:** Dispatch baseline HEAD `85eb094aaedaf518e0184767f25812a8a3c3b10a`; the working tree was already dirty, as recorded in `docs/execution/context.md:19`.

## Confirmed: F-SKILL-001 — symlinked path escapes Skill Store root during promotion cleanup

- **Severity:** Medium (confirmed from Phase 1 candidate)
- **Exact defect locations:** `zink-skill-store/src/catalog.mjs:1640-1658` validates only the identity grammar (SLUG strings) before any path use, and `:1720-1733` builds `versionDir`/`parentDir` from the caller's root and calls `healWriterResidue`, which runs before the catalog scan at `:1843-1865`. Inside that helper, `:1331-1341` does `readdir(parentDir)`, accepts matching `.pending-`/`.stranded-` names through `isResidueDirectory` at `:1077-1083`, and recursively removes the child. No `realpath`/containment check runs on the identity path first; the only `realpath` in the scan is the root resolution at `:877`.
- **Refusal sites (later, so they cannot prevent the delete):** a symlinked root is refused at `:868-875` (`UNSAFE_PATH`); a symlinked root entry at `:728-731` and a symlinked intermediate entry at `:800-808` are refused as `DIRECTORY_GRAMMAR_INVALID`. The `walk` entry check at `:689-712` is never reached for a linked child because the parent branch `continue`s before descending (`:800-808`). The Phase 1 report's `:689-710` locator therefore names a check that does not fire for this shape; the defect mechanism (cleanup at `:1331-1341` before the scan) is unaffected.
- **Reachability:** This is on the governed approval writer path, not an uncalled helper. OpenClaw loads the Skill Store door at `integrations/openclaw/plugins/zink-governance/index.mjs:1416-1465`, takes the store lock at `:1444`, and calls the door's promotion inside it. The door delegates to `promoteApprovedSkillUnlocked` at `zink-skill-store/index.mjs:61-69`. An identity whose namespace/capability path has a symlink ancestor therefore reaches cleanup before the scan refusal.
- **Effect:** A symlink at `skills/ns/cap` can redirect `readdir` and `rm` to an outside directory, so a child matching a version residue name is recursively deleted before the catalog refuses the linked path. This is a canonical-write/security defect in Skill Store ownership. It is conditional on a pre-existing ability to place a symlink inside the store tree, which is why it stays Medium. The boundary effect is that Tools' canonical `discover`, `read`, and `apply` arms then fail closed for the whole catalog: `zink-tools/adapters/skill-store/skill-adapter.mjs:418-451` returns `SKILL_CATALOG_INVALID` in discovery, and `loadVerifiedRecord` refuses any catalog diagnostic at `:170-183`, called by `read`/`validate` at `:541` and `apply` at `:612`. This does not establish that semantic `search` is disabled, because search uses the derived index.
- **Coverage evidence:** the scan-level refusal is already pinned — `tests/m6-t1-skill-store.test.mjs:390-403` asserts `DIRECTORY_GRAMMAR_INVALID` for a symlinked namespace entry and `:610-634` asserts a symlinked skill directory is refused on every lane. No shipped case drives `promoteApprovedSkillWithLock` into a symlinked identity and asserts the outside sentinel survives, so the pre-scan deletion path is untested while the refusal it precedes is green.
- **Fix blast radius:** Validate all path components below the resolved skills root before cleanup, or make the cleanup itself reject linked ancestors. A fix at the Skill Store writer/cleanup boundary affects canonical promotion and other Skill Store catalog state only. If implemented in the shared catalog walker instead, it affects Skill Store CLI/catalog consumers plus the Tools canonical read arms above. OpenClaw's approval protocol should remain a caller of the Skill Store door; changing its approval or lock contract would additionally affect the governance plugin and is unnecessary for this defect. **Fix-scope note:** the operator repair `quarantineInvalidVersion` (`zink-skill-store/src/catalog.mjs:1452-1497`) builds `versionDir`/`parentDir` from the caller's root the same way and its `lstat` only rejects a link as the final component, not a linked ancestor; a repair that changes only `healWriterResidue` leaves that sibling path unvalidated.
- **Duplicate/merge check:** Keep separate from `F-580` (`docs/execution/findings.md:1955-1966`): F-580 is a complete invalid canonical pair stranded after failed rollback; this candidate deletes matching residue through a symlink before catalog validation. `F-410` is scoped to temp files beside a version. Neither shares this path escape. Phase 1 `scan-skill-1` candidate `CAND-skill-1-01` is the same defect and should consolidate into `F-SKILL-001`, not become another row.

## Confirmed: F-SKILL-002 — alias identity persists raw while scoped search canonicalizes

- **Severity:** Medium (confirmed from Phase 1 candidate)
- **Exact writer locations:** The proposal adapter admits alias roots through `VETTED_ROOT_NAMESPACES` at `zink-tools/adapters/skill-store/skill-adapter.mjs:83-95,1110-1137`, and retains the original `parsedNamespace` in the durable proposal at `:1154-1176`. Owner approval binds that exact namespace at `integrations/openclaw/plugins/zink-governance/index.mjs:1312-1324` and passes it to promotion at `:1444-1465`. The Skill Store sync derives semantic metadata at `zink-skill-store/src/vector-sync.mjs:1216-1220`, but `buildSkillSyncTransaction` receives and writes the original namespace at `:565-576,622-627`.
- **Exact query locations and reachability:** `zink-tools/common/semantic-contract.mjs:36-44,203-210` maps `supply-chain` to `lscm`; the query resolver canonicalizes the filter at `:477-487`. `skill-adapter.mjs:720-751` puts those resolved values in `c.namespace @> ...`. The registered `zink_skill_search` path invokes `executeGovernedSkillQuery` at `integrations/openclaw/plugins/zink-governance/index.mjs:4394-4488`; governance permits a known alias/canonical namespace at `:3949-3984`. For a published `['supply-chain']` record, the index stores `['supply-chain']`, while both `supply-chain` and `lscm` filters become `['lscm']`; neither scoped predicate matches the row. Phase 1 `scan-skill-2` independently traced this same path; no PostgreSQL probe was run.
- **Effect:** A valid, owner-approved skill published under an alias root (for example `['supply-chain']`) is omitted from scoped semantic search under both the alias and the canonical spelling, and the registered model tool requires `namespace` (`integrations/openclaw/plugins/zink-governance/index.mjs:3949-3955,4418`), so the model cannot reach that skill through `zink_skill_search`. The adapter's other scoped arms disagree with each other too, though they are not model-registered: `discover` compares the stored namespace string exactly (`zink-tools/adapters/skill-store/skill-adapter.mjs:468-475`) and misses the record under `lscm`, while `read`/`apply` compare canonically (`assertNamespaceBinding`, `:256-280`) and serve it. A compound namespace cannot be scoped in search at all: the string form `supply-chain/inventory` is refused as `UNKNOWN_NAMESPACE_FILTER` (`zink-tools/common/semantic-contract.mjs:477-487`) and the array form is refused as `SKILL_NAMESPACE_FILTER_INVALID` because `inventory` is not a resolvable segment (`skill-adapter.mjs:731-745`), while governance's exact catalog also lists no compound spelling (`integrations/openclaw/lib/policy.mjs:581-626`; gate at `index.mjs:3959-3975`), even though the catalog admits up to eight namespace segments (`zink-skill-store/src/catalog.mjs:337-347`; README example `zink-skill-store/README.md:193`). This is a false negative; evidence does not show cross-namespace disclosure, state deletion, or a component outage. The issue is exactly the persisted identity/query contract mismatch, not `F-015`'s REFUTED capability-case premise. The `discover` split is an adjacent adapter site of the same contract disagreement; triage may widen this row or file it separately, but it must not be dropped as covered.
- **Fix blast radius:** A query-side fix that matches raw approved aliases to their canonical namespace is confined to the Tools Skill adapter's SQL predicate and returned-hit contract; it preserves canonical filesystem identity and Skill Store state. Do not canonicalize `skills.catalog_index.namespace` in the writer without also revising tombstone identity: `zink-skill-store/src/vector-sync.mjs:765-787` builds tombstone keys from the manifest identity and SQL row namespace. Canonicalizing the durable manifest/path instead would change Skill Store identity, proposal bindings, policy namespace names, and existing records; that needs an explicit owner decision and a migration/compatibility plan. Changing the shared alias map in `semantic-contract.mjs` affects both Skill Store embedding derivation (`vector-sync.mjs:11-16`) and Tools query/adapter behavior, as well as the packaged runtime list at `integrations/openclaw/lib/policy.mjs:1757-1774`.
- **Duplicate/merge check:** No existing register row covers this raw namespace-alias write/query mismatch. Keep distinct from `F-015` (capability case, REFUTED at `docs/execution/findings.md:135-146`), `F-434` (per-row freshness, `:928-939`) and `F-572` (stored model identity, `:1890-1901`). Phase 1 `scan-skill-2` observation is the same candidate as `F-SKILL-002`; merge it there, not into another finding.

## New candidate — a nested namespace is admitted at propose and cannot be scoped at search

- **Severity:** Medium
- **Exact locations:** Skill Store admits 1–8 namespace segments as SLUGs, with no depth restriction beyond that (`zink-skill-store/src/catalog.mjs:337-347`), and its README documents a nested identity (`zink-skill-store/README.md:193`). The Tools proposal path checks only the ROOT segment against `VETTED_ROOT_NAMESPACES` (`zink-tools/adapters/skill-store/skill-adapter.mjs:1110-1123`), then derives metadata; an unresolved deeper segment does not block it because the domain comes from the resolvable root and passes the `CANONICAL_DOMAINS` gate (`zink-tools/common/semantic-contract.mjs:228-269`; adapter gate at `:1125-1137`). The model-facing `zink_skill_propose` gate performs no namespace check at all (`integrations/openclaw/plugins/zink-governance/index.mjs:3986-4000`).
- **Contradicting consumer side:** `search` cannot express that identity in any spelling. Governance requires every supplied element to be an exact member of `GOVERNED_SKILL_NAMESPACE_CATALOG`, which lists only single root domains and aliases (`integrations/openclaw/lib/policy.mjs:581-626`), and rejects anything else with `NAMESPACE_ACCESS_DENIED` (`index.mjs:3959-3975`); the array form with a deeper segment is additionally rejected by the adapter's semantic resolution as `SKILL_NAMESPACE_FILTER_INVALID` (`skill-adapter.mjs:731-745`), and the slash-joined string form is refused as `UNKNOWN_NAMESPACE_FILTER` (`semantic-contract.mjs:477-487`).
- **Effect:** An agent can propose a nested-namespace skill that the owner can approve and that will enter the canonical store and derived index, yet no scoped `zink_skill_search` call can select it; the tool's own `namespace` requirement (`index.mjs:3949-3955,4418`) means the model has no fallback. This is a propose/search contract asymmetry at the boundary, distinct from `F-SKILL-002`'s alias-persistence mismatch: canonicalizing aliases would not make a nested namespace scopable, and widening the scope vocabulary would not fix the alias write/query split.
- **Fix blast radius:** If nested namespaces are intended to be searchable, the scope vocabulary and the adapter's filter resolution must gain depth (affecting `GOVERNED_SKILL_NAMESPACE_CATALOG`, `evaluateToolAccess`, `prepareQueryEmbedding`/`deriveSemanticMetadata`, and the adapter predicate) while Skill Store identity stays unchanged. If they are not intended, `propose` must refuse a nested namespace before the durable proposal is written, which changes the model-visible proposal contract and must align with Skill Store admission so an operator path cannot create the same unsearchable record. Either direction touches OpenClaw policy, Tools query contract, and Skill Store admission — a coordinating decision, not a one-file fix. Do not "fix" it by canonicalizing or flattening the stored identity.
- **Duplicate check:** No live register row covers namespace depth or the propose/search representable-set mismatch (register search for the scope catalog and nested-namespace terms returned no row). Keep separate from `F-SKILL-002` and from the `F-435` public-door item.

- **Skill Store -> Tools side of the same cause:** `infrastructure/docker/compose/compose.core.yml:13-16` initializes the cluster as `POSTGRES_USER: postgres`; n8n uses a separate `n8n` role at `:65-72`. `zink-skill-store/src/vector-sync.mjs:307-315,321-336` invokes `docker exec ... psql -U postgres -d postgres`. The public door exposes the migration/sync functions (`zink-skill-store/index.mjs:41-52,91-95`), the approval path invokes them at `integrations/openclaw/plugins/zink-governance/index.mjs:1165-1188`, and the Tools adapter imports the same executor from Skill Store internals at `zink-tools/adapters/skill-store/skill-adapter.mjs:13-24`, reaching it on search at `:779-806`.
- **Why the Tools link matters for that fix:** A remediation that reduces only the Skill Store sync/migration client leaves the Tools retrieval path on the widened executor. The current search statement is a `SELECT` (`skill-adapter.mjs:779-804`), so this is a privilege-boundary exposure, not evidence of a model-controlled arbitrary SQL route. Preserve `skills.*` schema and ledger ownership and keep Tools a read-only consumer; do not move `skills.*` DDL to Knowledgebase or grant Tools write access.

## Boundary and operational cross-check

- **Canonical vs derived state:** The Skill Store contract makes the Git-native manifest/content the source of truth and pgvector derived (`docs/contracts/skill-store/agent-skill-store.md:15-26,145-149`). The Skill Store migration runner owns `skills.schema_migrations` and does not access `knowledge.schema_migrations` (`zink-skill-store/src/migrations.mjs:16-29,68-93`). The inspected vector SQL targets `skills.*`; no Knowledge index or table mutation was found from this boundary.
- **Tools ownership leak already registered:** Tools still imports Skill Store `src` internals (`skill-adapter.mjs:13-24`) while the store publishes `zink-skill-store/index.mjs`. This is already covered by `F-435` at `docs/execution/findings.md:941-952`, including the adapter import and the requirement to route through the store door. Do not file a duplicate. The public door currently lacks a query API, so any remediation must explicitly preserve the governed Tools retrieval contract rather than silently moving the model-visible surface into Skill Store.
- **Proposal/governance and error semantics:** Proposal content is stored as `CANDIDATE`, owner approval binds proposal identity and content digest, and only trusted promotion writes canonical files (`agent-skill-store.md:123-149`; approval evidence above). Tools exposes `search`/`propose` and excludes publish/deprecate/admin in `skill-adapter.mjs:69-79`; adapter failures are returned as fixed, controlled failure messages at `:1277-1299`. No new governance bypass or error-shape defect was established in this trace.
- **Namespace authorization limit:** Governance checks that skill search names a namespace from the global governed catalog and blocks `all` (`index.mjs:3949-3984`); action permissions are per agent in `policy.mjs:498-576`. No contract or architecture source reviewed here defines per-agent namespace allowlists, so the global catalog behavior is not reported as an additional authorization defect.
- **Runtime/startup:** There is no separate Skill Store Compose service, port, volume, or healthcheck. PostgreSQL has a healthcheck (`compose.core.yml:19-24`); Knowledge/n8n have declared healthy-DB dependencies (`:62-64,145-147`). Skill Store DB access is on demand through `docker exec`. The plugin applies Skill Store migrations before vector sync at `index.mjs:1165-1188`; the already-registered unlocked migration/sync concerns are `F-431` (`findings.md:889-900`) and `F-436` (`:954-965`), not duplicates of the two requested findings.
- **Backup coverage:** The general backup defaults to PostgreSQL databases `n8n` and `postgres` and dumps each at `infrastructure/docker/scripts/backup.ps1:7-12,100-110`; this covers the derived `skills.*` tables in `postgres`. It does not archive the canonical Git-native `zink-skill-store/skills/` source tree, and no Skill Store restore procedure was found in the inspected runbooks. The repository describes that tree as the canonical tracked record (`agent-skill-store.md:15-26`), but this inspection does not establish the Git remote's retention/restore guarantees or that no operator backup exists outside the repository. Treat canonical source-tree backup coverage as **not evidenced here**, not as a proven data-loss finding.
