## Confirmed boundary finding

### F-KB-004 — API serializers withhold index liveness and stable segment identity from retrieval/citation consumers

- **Category:** F5 — Data Integrity & Result Correctness
- **Related register item:** `F-KB-004` at `docs/execution/findings.md:2098-2109`; related closed predecessor `F-573`, recorded at `CHANGELOG.md:2160-2161`.
- **Affected modules:** Zink Knowledgebase API and Zink Tools Knowledge adapter / its declared output contract. OpenClaw governs and packages this Tools adapter but does not own Knowledge state.
- **Severity:** Medium (as registered)
- **Verdict:** Distinct live defect; the database-layer part of F-573 is closed, but its caller-visible criterion is incomplete. F-KB-004 is not an unsupported duplicate.
- **Root cause:** The Knowledgebase loader was extended with index state and ordinal, but `/v1/chunk` and `/v1/citation` construct explicit response rows without those properties. Tools' adapter also projects only search result fields, and its closed result schema has no corresponding index-state or stable-identity fields. The end-to-end consumer contract therefore cannot deliver F-573's promised status/identity.
- **Exact evidence:** `apps/knowledge/app/database.py:1913-1925` selects `indexes.status` while retrieving any segment by ID without an ACTIVE-only condition; `:1961-1967` returns `index_status` and `chunk_ordinal` in `SegmentRecord`. The live serializers omit both: `/v1/chunk` row `apps/knowledge/app/main.py:958-977`, `/v1/citation` row `:998-1026`; the metadata route also omits both at `:1039-1068`. The selected segment may be from a superseded index, and cleanup explicitly deletes its segments at `apps/knowledge/app/database.py:2377-2407,2591-2609`, so a citation can remain syntactically present without liveness state, while the surrogate segment ID will later disappear.
- **Cross-boundary confirmation:** Tools dispatches the retrieve/citation routes in `zink-tools/adapters/knowledge/knowledge-adapter.mjs:409-419`; its success formatter maps fields into a fresh object and does not copy `index_id`, `indexed_by_run_id`, `index_status`, or `chunk_ordinal` (`:775-822`). The declared closed output item permits only `chunk_id`, title/text/score/citation, and metadata fields for path/source/span (`zink-tools/contracts/tools/zink-knowledge.schema.json:85-119`); metadata rejects all other keys at `:114`. The adapter drops the endpoint's top-level `index_id`/`indexed_by_run_id` too: its formatter receives result rows and never reads those top-level values (`knowledge-adapter.mjs:716-822`), despite the Knowledge endpoints returning them (`apps/knowledge/app/main.py:978-984,1028-1034`). This is a potentially incomplete caller-visible portion of F-071's closure, but it is a separate envelope-mapping seam; it does not account for the F-573 status/ordinal omission and is not counted as another F-KB-004 defect. For search, Knowledge supplies source ID/digest/span but no index status or ordinal (`apps/knowledge/app/main.py:793-848`), and Tools forwards provenance identity but not index fields (`knowledge-adapter.mjs:798-821`). Therefore adding fields to Knowledge's retrieve/citation JSON alone would not satisfy the model-facing Tools contract.
- **Existing coverage and closure analysis:** F-573's tests exercise only the loader values and SQL column at `apps/knowledge/tests/test_m12_t9_b5_db_retrieval.py:225-280`; they do not assert HTTP serialization. The HTTP regression at `apps/knowledge/tests/test_b5_knowledge_http_surface.py:347-382` asserts only digest and span. `CHANGELOG.md:2160-2161` says the loader change lets a caller distinguish superseded hits and re-derive by `(index, source digest, ordinal)`, but that caller-facing data is not asserted or delivered through either API serializer. `F-570` independently established the API-to-Tools provenance contract pattern for source id/digest/span (`CHANGELOG.md:2228-2229`), yet its schema and adapter field set has none of F-573's fields. F-071 (`CHANGELOG.md:1461-1463`) concerned missing routes and dropped index/run attribution and is closed; the routes now exist and emit top-level `index_id` / `indexed_by_run_id` (`main.py:978-984,1028-1034`). That older defect does not cover segment status or ordinal at row and adapter output.
- **Reproduction:** Static response-shape trace; no database request was run. A segment whose fetched row has `index_status='SUPERSEDED'` and `chunk_ordinal=7` produces a `SegmentRecord` with those values (`database.py:1961-1967`); the two row dictionaries omit them (`main.py:958-977,998-1026`). Under the actual adapter projection, absent upstream properties cannot be forwarded, and the schema cannot represent them (`knowledge-adapter.mjs:775-822`; `zink-knowledge.schema.json:85-119`). The existing F-573 loader unit test's SUPERSEDED/ordinal 7 example confirms the database-side values at `test_m12_t9_b5_db_retrieval.py:235-280`.
- **Fix blast radius:** The serializer omission at `apps/knowledge/app/main.py:958-977,998-1026,1039-1068` affects Knowledgebase HTTP consumers, including all callers of retrieve/citation/metadata; preserve existing search and citation provenance fields and error semantics. Carrying those fields through Tools requires a coordinated change to `zink-tools/adapters/knowledge/knowledge-adapter.mjs:775-822` and the closed output schema `zink-tools/contracts/tools/zink-knowledge.schema.json:85-119`, plus its consumers and adapter/schema regression tests. These are two distinct owners: Knowledgebase owns status/ordinal truth and its API; Tools owns its projection/output contract. Do not have Tools query or mutate `knowledge.*` directly, or transfer Knowledge's index lifecycle to Tools. Search results also need a coherent representation if the advertised `zink_knowledge_search` result must be re-verifiable after downstream use; Knowledge's search projection and the adapter's search formatter/schema are separate sites to assess under the accepted fix contract. OpenClaw registry/package policy declares the Tool as read-only (`integrations/openclaw/lib/policy.mjs:2580-2594`) and packages the adapter as an asset (`:1757-1774`), so a Tools adapter change may also require the host's packaged asset verification/update path; the host does not gain ownership of Knowledge data.
- **Acceptance criteria for triage:** For superseded and active segment fixtures, the public Knowledge API exposes enough status and stable segment identity to distinguish liveness and re-derive `(index, source revision, ordinal)` after cleanup. The Tools adapter and closed contract preserve that information to the consumer, with malformed/missing fields handled explicitly and no fabricated identity. Regression coverage crosses the actual Knowledge response -> Tools adapter -> declared output schema and checks both modules standalone. Resolve F-071's index attribution separately or explicitly incorporate its undelivered `index_id` into the related compatibility review; do not treat top-level run attribution and row liveness/ordinal as one root cause.

## Other boundary checks

- **Search citation identity:** Search results publish segment ID, source ID, source digest and line/page span at `apps/knowledge/app/main.py:793-818,827-848`; Tools requires chunk identity plus a non-empty citation before returning any evidence at `zink-tools/adapters/knowledge/knowledge-adapter.mjs:720-749` and forwards digest/source/span in metadata at `:798-821`. The contract declares those identity fields at `zink-tools/contracts/tools/zink-knowledge.schema.json:90-119`. This aligns with F-570's recorded closure (`CHANGELOG.md:2228-2229`); no separate defect supported here.
- **Search completeness:** The Knowledgebase returns retained/returned/candidate counts and truncation flags at `apps/knowledge/app/main.py:870-880`; Tools conditionally forwards those fields at `knowledge-adapter.mjs:825-869`, and they are declared in the output schema at `zink-knowledge.schema.json:121-138`. No boundary defect found in this field set.
- **Endpoint and access path:** The adapter uses a configured/default HTTP endpoint with a hostname allowlist (`knowledge-adapter.mjs:76-128,321-347,405-435`); Compose hosts Knowledge on the platform bridge with its own health check and PostgreSQL dependency (`infrastructure/docker/compose/compose.core.yml:136-183`), and Nginx routes `/knowledge/` to the Knowledge service while refusing other paths (`infrastructure/nginx/conf.d/default.conf:10-22,45-47`). No direct Tools access to the Knowledge database or shared mutable state was found in the reviewed paths. Tools routes reads to the API; Knowledge keeps its own database and index lifecycle.
- **Phase 1 reports:** `scan-kb-3.md:22-32` identifies the same API serializer omission as F-KB-004; `scan-kb-1.md:10-20` and `scan-kb-2.md:12-22` identify unrelated Knowledge ingestion and migration candidates. `scan-tools-1.md:8-25` and `scan-tools-3.md:8-27` report no new adapter defect and check existing contract/error items; `scan-tools-2.md:8-26` confirms the schema-only compute capabilities are intentionally non-executable. None contradicts this boundary finding; the omission crosses the otherwise-consistent provenance path after the API row is serialized.
