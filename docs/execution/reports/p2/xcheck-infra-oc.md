## Boundary topology and shared controls

- `infrastructure/docker/compose/compose.core.yml:9-32,58-105,107-135,136-183,216-226` defines PostgreSQL, n8n, Nginx, and Knowledge on the project-scoped `platform` bridge, with only `n8n-data` and `postgres-data` named volumes. It declares no OpenClaw service, OpenClaw volume, or OpenClaw network attachment. `infrastructure/docker/scripts/start.ps1:16-20,33-49,83-91` starts only those Compose files/profiles.
- OpenClaw setup writes its state under the operator home (`integrations/openclaw/configure.mjs:1566-1587,1590-1647`); its generated gateway is a systemd user service and pins `MemoryMax=768M` (`integrations/openclaw/lib/policy.mjs:1979-1989`). OpenClaw gateway bind is loopback with token auth (`integrations/openclaw/lib/policy.mjs:1349-1355`). Its per-agent Docker sandboxes set network `none`, read-only root, and drop all capabilities (`integrations/openclaw/lib/policy.mjs:1408-1419`), but the README explicitly says the gateway/channel/plugin are outside those sandboxes (`integrations/openclaw/README.md:12-21`).
- Thus the Knowledge container's Compose network/privilege settings do not govern the OpenClaw gateway or its plugin host process. A host-wide firewall or routing change could affect OpenClaw's outbound Discord/router connectivity; a Compose-only network change does not. This matters when implementing egress remediation.

## F-INFRA-001 — deployed Knowledge direct egress

**Cross-check: corroborated at configuration level; actual public/host reachability not measured.** The Knowledge service joins `platform` and receives a `host.docker.internal:host-gateway` mapping while its model URL points at the allowlisted Nginx path (`infrastructure/docker/compose/compose.core.yml:157-165,182-183`). The deployed `platform` declaration is a plain bridge, not `internal: true` (`infrastructure/docker/compose/compose.core.yml:216-222`; also `infrastructure/networking/networks.yml:23-25`). This leaves a configured direct egress path outside Nginx policy; host firewall behavior remains unknown. Nginx only admits the exact tags/embed routes and refuses other paths (`infrastructure/nginx/conf.d/default.conf:24-47`). The live proof checks configured gateway route/refusals (`infrastructure/docker/scripts/knowledge-t5-common.ps1:570-588`) but does not test direct public TCP/DNS; those probes exist only in the acceptance isolation check (`:591-609`). The live overlay also does not remove Knowledge's core `extra_hosts` mapping (`infrastructure/docker/compose/compose.m4-t5.live.yml:1-17`), while the acceptance overlay explicitly resets it and marks its network internal (`infrastructure/docker/compose/compose.m3-t5.acceptance.yml:26-41,52-63`).

- **Reachability and blast radius:** This is a Knowledge container egress defect. Nginx and Knowledge are the infrastructure-side services implicated by a containment fix. Making the shared platform network internal or applying a host-wide egress policy can also disrupt Nginx's host Ollama route (`default.conf:29-43`) or unrelated host applications; the OpenClaw user service is not attached to this Compose network. If remediation uses host-wide policy, separately preserve OpenClaw's configured router and Discord connectivity. Do not describe F-INFRA-001 as an OpenClaw path or as an effect on its private governance state.
- **Disposition:** Retain Medium candidate pending the Phase 3 live probe and triage; static declarations alone do not establish the host firewall's effective reachability.

## Other boundary checks

- **OpenClaw -> Knowledge contract:** the governance plugin defaults to `http://127.0.0.1:8080/knowledge` (`integrations/openclaw/plugins/zink-governance/index.mjs:4572-4584`), and Nginx publishes `8080` on host loopback (`infrastructure/docker/compose/compose.core.yml:107-123`). This is consistent with OpenClaw running as a host/WSL user service; no container DNS name is assumed by the plugin. The Nginx route strips `/knowledge/` and proxies to Knowledge (`infrastructure/nginx/conf.d/default.conf:10-22`). Static review found no additional endpoint or error-contract mismatch. Actual WSL-to-Docker Desktop loopback behavior was not probed.
- **Startup/health:** Infrastructure `start.ps1` waits for healthy PostgreSQL before completing Compose startup (`:83-91`); Knowledge depends on healthy PostgreSQL and Nginx/Knowledge use their own healthchecks (`compose.core.yml:19-24,123-177`). OpenClaw's `verify.mjs` performs separate live gateway, Discord, sandbox and router checks (`integrations/openclaw/verify.mjs:677-751`). No shared Compose startup dependency or cross-runtime health gate is declared.
- **Backup/state ownership:** Infrastructure `backup.ps1` covers PostgreSQL databases and n8n home (`infrastructure/docker/scripts/backup.ps1:89-117,148-160`); it does not claim to back up OpenClaw's host state. OpenClaw's own `runtime-backup.mjs` selects OpenClaw config, workspaces and governance extension data (`integrations/openclaw/topology/lib/runtime-backup.mjs:340-408,444-460`). Compose backup is not evidence of OpenClaw-state coverage; preserve the independent owner-specific recovery path.
