## F-INFRA-002 — shared PostgreSQL administrator identity reaches Knowledge and Skill Store

- **Category:** F2 — Security & Authorization
- **Affected modules:** Infrastructure, Zink Knowledgebase, Zink Skill Store. Zink Tools is the Skill Store query adapter/caller; n8n's separate database is a collateral tenant.
- **Severity:** High (as registered)
- **Cross-check verdict:** Confirmed static access paths; no live privilege probe. The finding's original Knowledge credential evidence is valid but incomplete: the Skill Store client also executes as `postgres`.
- **Root cause:** A PostgreSQL cluster administrator is used as a routine database identity by both Knowledge and Skill Store clients. Knowledge receives the `postgres` password in Compose; Skill Store's executor invokes `psql -U postgres` inside the PostgreSQL container. Each module has its own schema and migration ledger, but those boundaries are not enforced against these client identities by the evidenced configuration.
- **Evidence:** `infrastructure/docker/compose/compose.core.yml:13-18` initializes PostgreSQL with database/user `postgres` and persistent `postgres-data`; `:149-153` supplies Knowledge with that same user and the cluster password. Knowledge uses its configured connection pool at `apps/knowledge/app/database.py:453-459` and performs migration DDL through it at `:2757-2768,2790-2819`. Separately, `zink-skill-store/src/vector-sync.mjs:307-335` starts `docker exec ... psql -U postgres -d postgres`, and `:407-409` sends the SQL through that client. The Skill Store migration runner creates/uses `skills.schema_migrations` and its schema via this executor (`zink-skill-store/src/migrations.mjs:75-92,201-205,227-228,261-262`); derived writes target `skills.catalog_index` and `skills.segments` at `zink-skill-store/src/vector-sync.mjs:616-667`. The Zink Tools Skill adapter imports that executor (`zink-tools/adapters/skill-store/skill-adapter.mjs:13-20`) and runs a `SELECT` over `skills.*` at `:779-806`, so Tools reaches this database boundary through the designated Skill Store retrieval adapter. The independent n8n login/database is bootstrapped at `compose.core.yml:65-72` and `infrastructure/docker/scripts/bootstrap-postgres.sh:28-42`.
- **Reproduction:** Static trace only. No database role query or cross-schema read/write probe was run; actual role attributes and runtime authentication remain unprobed.
- **Acceptance criteria for triage:** Constrain routine Knowledge and Skill Store database identities to their own required objects and migration capabilities. Prove Knowledge cannot administer the cluster or access `skills.*`/n8n-owned data, and Skill Store cannot mutate `knowledge.*` or n8n-owned data. Preserve separate `knowledge.*` and `skills.*` schema/ledger ownership and n8n's separate login/database.
- **Fix blast radius:** Changing `compose.core.yml:149-153`, PostgreSQL bootstrap/role grants, or credential delivery affects Knowledge startup, pool access and Knowledge migrations (`apps/knowledge/app/database.py:453-459,2757-2819`) plus Skill Store sync and migrations (`zink-skill-store/src/vector-sync.mjs:307-335,407-409`; `zink-skill-store/src/migrations.mjs:75-92,201-265`). Changing the Skill Store executor affects Skill Store migration/sync and the Tools Skill adapter that imports it (`zink-tools/adapters/skill-store/skill-adapter.mjs:13-20,779-806`). Role/bootstrap changes must preserve n8n's login and database (`compose.core.yml:65-72`; `bootstrap-postgres.sh:28-42`). Keep Knowledge migrations from applying Skill Store DDL and keep Tools on its approved retrieval adapter; do not turn Tools into an owner or direct mutator of either schema. Any privilege reduction must account for each module's standalone schema migration/startup path; extension provisioning also appears in Knowledge migration `apps/knowledge/migrations/001_initial.sql:1`.
- **`scan-skill-3` pointer:** Its pointer to `compose.core.yml:148-153` and `apps/knowledge/app/config.py:40-45` is correctly routed to the database/infrastructure cross-check. The `compose.core.yml` credential is confirmed; this report adds the distinct Skill Store client path above. The Knowledge config default at `apps/knowledge/app/config.py:40-45` is only a fallback declaration and is not itself separate evidence of runtime use.

## F-DB-002 — n8n encryption-key backup omission is independent

- **Category:** F5 — Data Integrity & Result Correctness
- **Affected surface:** Infrastructure backup and n8n workflow runtime at the OpenClaw/n8n hosting boundary; it does not establish an omission in Skill Store or Tools state.
- **Severity:** Medium (as registered)
- **Cross-check verdict:** Separate root cause from F-INFRA-002. The former is a database privilege boundary; this item is absent recovery material for n8n credentials and is conditional on loss of the externally retained key.
- **Evidence:** `infrastructure/docker/scripts/backup.ps1:113-127` archives `/home/node/.n8n` while excluding `config`; its manifest enumerates only files under the backup root (`:138-158`). The runtime obtains `N8N_ENCRYPTION_KEY` externally at `infrastructure/docker/compose/compose.core.yml:80`; `README.md:444-448` directs the operator to configure that key in the environment file. `docs/execution/findings.md:2261-2264` records that no secure recovery reference is included and external operator retention is unverified. The standard backup's database set is `n8n` and `postgres` (`backup.ps1:7-13,101-110`), but that does not supply the matching encryption key.
- **Reproduction:** Not run; restoring encrypted n8n credentials with a different key was not attempted.
- **Fix blast radius:** Changes to `backup.ps1:113-158`, its manifest or recovery documentation affect infrastructure backup and n8n recovery. Preserve secret-exclusion behavior. This does not require changing Knowledge/Skill Store database roles, schemas or writers.

## Backup and boundary assessment

- **Skill Store state:** The general infrastructure backup dumps the full `postgres` database (`infrastructure/docker/scripts/backup.ps1:7-13,101-110`), which contains both `knowledge.*` and derived `skills.*`; `docs/execution/reports/p1/scan-skill-3.md:15-18` confirms the scan found no Skill Store backup utility and distinguishes that full-database archive from the Knowledge-only drill. Canonical Skill Store lifecycle records (`SKILL.md` and `manifest.json`) are Git-native, with PostgreSQL vectors derived from them (`docs/contracts/skill-store/agent-skill-store.md:13-25,43-58,145-149`; `zink-skill-store/README.md:128-143`). No evidence in this audit establishes loss or omission of canonical Git state, so the lack of a Skill Store-specific restore command is not reported as a data-loss defect.
- **Knowledge recovery neighbor:** F-DB-001 is bounded to the Knowledge T5 recovery archive: `infrastructure/docker/scripts/knowledge-t5-live.ps1:284,288-289,330-332,362-364,396` scopes the archive/check to `knowledge` and can certify without comparing `segments` data. It does not demonstrate that Skill Store data is omitted from the general PostgreSQL dump and does not make Knowledge the owner of `skills.*`.
- **Tools state:** No Tools-owned persistent Knowledge/Skill database state or backup omission was evidenced. The Skill adapter reads the Skill Store's derived index through the intended retrieval surface; architecture says Tools owns no persistent Knowledge/Skill internals (`docs/architecture/platform-boundaries.md:14-23`).
- **Network/environment:** PostgreSQL, Knowledge, n8n and other Compose services join the project-scoped `platform` bridge (`infrastructure/docker/compose/compose.core.yml:31-32,104-105,133-134,182-183,216-222`); PostgreSQL has no host-published port in this Compose file. The bridge does not enforce database schema privileges. No separate Skill Store or Tools Compose service/port/credential binding was found in the inspected runtime definitions. Skill Store uses the `POSTGRES_CONTAINER` process setting or `personal-tool-postgres-1` default (`vector-sync.mjs:312-315`), not a module-specific database credential. This reinforces the F-INFRA-002 access review; it does not evidence another network or configuration defect.
- **Restore contracts:** `docs/runbooks/knowledge-platform.md:51-65` describes the generic PostgreSQL/n8n backup and explicitly states ordinary restore automation is not implemented. That disclosed limitation is not, by itself, evidence of a second Skill Store recovery defect. The n8n key omission remains the concrete F-DB-002 issue.

- **F-DB-002:** Confirmed as a separate, conditional n8n recovery-material issue; no Skill Store/Tools connection evidenced.
- **F-DB-001:** Knowledge-only restore-verification issue; not a shared Skill Store/Tools root cause.
- **Additional findings:** None. No source changes, tests or runtime probes performed.
