## Confirmed candidate

### CAND-xcheck-tools-oc-01 — Excel ZIP validation permits unbounded aggregate expansion across declared entries

- **Category / severity:** F6 — Reliability & Performance / High.
- **Status:** Confirmed by static runtime path; no resource-exhaustion probe was run.
- **Path and evidence:** `integrations/openclaw/lib/artifact-validator.mjs:153-206` trusts the central-directory entry count (`:164`), loops over every entry (`:168-204`), inflates each declared stream separately with only `maxOutputLength: MAX_ARTIFACT_SIZE_BYTES` (`:191-198`; 25 MiB at `:64-79`), and retains each resulting buffer in `contents` (`:167,191-198`). No aggregate expanded-byte or entry-count budget is applied. The input artifact is size-bounded before being read (`:784-808`), but that only limits compressed input bytes. The Excel validator calls `readZipArchive(contentBuf)` (`:892-930`, especially `:907`), and the production result path reaches `evaluateResultGate` (`integrations/openclaw/plugins/zink-governance/index.mjs:3125-3134`). The `execution_finished` handler accepts artifact paths from the event, resolves them against the governed sandbox, and calls `handleExecutionFinished` (`index.mjs:10022-10100`), which supplies the artifact to the result gate. Thus an archive supplied as a governed execution result reaches this runtime parser; this is not merely an inert schema limit.
- **Concrete static reproduction:** A sub-25-MiB ZIP can declare many distinct central-directory names that point at one small local deflate stream. The parser inflates and retains a new buffer for each distinct name, up to 25 MiB each; the 16-bit central-directory count permits 65,535 entries, a theoretical aggregate over 1.5 TiB. This follows from the parser's loop and per-entry cap; no fixture or runtime probe was executed.
- **Impact:** A delegated result archive can consume excessive OpenClaw memory and CPU during validation, disrupting unrelated OpenClaw work. The defect is in runtime Excel artifact validation; the four math capability schemas remain schema-only and are not involved.
- **Fix-site blast radius:** The bounded expansion check belongs at the OpenClaw ZIP-reader/Excel-validation boundary. If entry-count handling is shared or changed for all reader modes, review Power BI and DOCX callers of the same helpers (`artifact-validator.mjs:138-139,219-233,522-523,1139-1143`); if only content inflation is bounded, Excel sheet validation is the direct runtime consumer. Do not move ZIP parsing or execution budgets into Zink Tools' call schema: that would change the peer module's public artifact contract without removing the OpenClaw runtime path. No Knowledgebase or Skill Store state is affected.
- **Existing finding check:** F-502 is a separate, unwired artifact publisher and is not this parser path. F-563 is a Discord preview output-path check, not ZIP expansion. Phase 1 `scan-oc-2.md:10-20` independently identified this candidate and cited the same reachable Excel validation path.

## Low contract candidate

### CAND-xcheck-tools-oc-02 — Excel semantic contract says unimplemented while the hosted tool executes the writer

- **Category / severity:** F4 — Integration & Contract Violations / Low.
- **Status:** Confirmed documentation/runtime contract mismatch; no execution failure was observed.
- **Path and evidence:** `zink-tools/excel/contract.md:5-9,13-24` describes the interface and says under Model A invocation returns deterministic `ENGINE_NOT_IMPLEMENTED` (`:24`). In the same working tree, `zink-tools/README.md:7-9` calls Excel a real engine and locates it at `integrations/openclaw/lib/excel-writer.mjs`. The actual registered tool resolves that writer and invokes `executeExcelOperation(params, sandboxDir)` (`integrations/openclaw/plugins/zink-governance/index.mjs:4845-4869`); the writer validates the sandbox target and writes the workbook (`integrations/openclaw/lib/excel-writer.mjs:640-674,841-852`). The guard's `contractOnlySeam` at `guard.mjs:2234-2239` is an authorization/contract seam; the live plugin hook then permits the separately registered native tool, whose execution path is explicitly distinguished at `index.mjs:8372-8380`. The runtime schema is also active for call validation (`guard.mjs:1888-1900`) and defines operation-specific input branches (`zink-tools/contracts/tools/zink-excel.schema.json:8-53`); this is not a schema-only capability.
- **Impact:** An implementer or operator reading the Zink Tools semantic contract is told that calls are unimplemented even though the hosted runtime writes workbooks. This obscures which behavior and output contract callers can rely on; no runtime failure follows solely from the stale statement.
- **Fix-site blast radius:** Correcting the Zink Tools contract text to match the hosted writer preserves current runtime behavior but changes the published semantic contract consumed by OpenClaw and its tool authors. Making the OpenClaw executor return `ENGINE_NOT_IMPLEMENTED` to match the current sentence would disable the live Excel writer and change the user-visible capability. Resolve intended Excel mode before changing runtime or schema; keep the workbook engine and its filesystem authority in the OpenClaw hosting boundary unless ownership is explicitly changed.

## Existing cross-boundary findings and duplicate assessment

- **F-546 — packaged Tools adapters are not guaranteed reachable from the deployed plugin resolver (OPEN).** The packager includes `zink-tools/adapters/knowledge`, `skill-store`, `n8n`, SQL modules and shared contracts in `PACKAGED_RUNTIME_MODULES` (`integrations/openclaw/lib/policy.mjs:1757-1774,1833-1840`). However, the plugin's `findRepoRoot` candidates are environment root, a repository-depth path and cwd (`integrations/openclaw/plugins/zink-governance/index.mjs:691-697`); its ancestor walk checks each parent but not the plugin root itself (`:699-705`). The guard's shared resolver checks configured roots, a repository-depth path and cwd, but not the packaged plugin root (`integrations/openclaw/topology/lib/guard.mjs:390-426`). Therefore the digest-gated packaged copies are not themselves resolver candidates; loading in an isolated deployed layout depends on the host cwd or another repository root being available. This is the same packaging/root-resolution mechanism already recorded by F-546 (`docs/execution/findings.md:1669-1680`), not a new row. **Blast radius:** an OpenClaw resolver/packaging fix affects all hosted Tools adapter loads and governance readiness, while the Tool schemas, public adapter signatures, and domain persistence ownership should remain unchanged. The exact installed-host cwd was not available to this static audit.
- **F-562 — logical versus absolute artifact path accept sets (OPEN).** The live guard validates tool-call paths with Zink Tools' relative logical-path validator (`integrations/openclaw/topology/lib/guard.mjs:1911-1932`), while the artifact result gate requires absolute paths (`integrations/openclaw/lib/artifact-validator.mjs:676-693`) and validates secondary members under a separate rule (`:1669-1687`). Existing F-562 documents the disjoint contract and single-member gate case (`docs/execution/findings.md:1825-1836`). This is a contract-boundary issue distinct from ZIP parsing. **Blast radius:** harmonizing path semantics affects the Zink Tools path contract/validator and OpenClaw artifact/result callers; preserve the sandbox and result containment guarantees when selecting one representation.
- **F-OC-003 and F-563 — related path-safety family, distinct sinks.** The Phase 1 Excel candidate reconstructs failed realpath resolution and later writes through a dangling symlink (`scan-oc-2.md:22-32`, `integrations/openclaw/lib/excel-writer.mjs:454-480,660-673,841-842`). The shared root-cause family is path containment being insufficient at the write site; neither finding is a duplicate of the other, and neither is the ZIP parser issue. A shared filesystem helper or policy change would affect both the Excel sandbox writer and Discord preview output under different roots; do not weaken either containment boundary to unify behavior.
- **F-502 — current observed implementation differs from the registered vulnerable pattern.** The current working-tree `publishArtifactAtomic` checks symlink components before creating directories (`integrations/openclaw/lib/artifact-validator.mjs:1768-1775`), creates its temp with `"wx"` (`:1778-1785`), and removes only a temp it created on failure (`:1808-1826`). Because the shell diff/status was denied and the baseline tree was dirty, this lane cannot attribute the observed implementation to committed HEAD versus pre-existing edits.
