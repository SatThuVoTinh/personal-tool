## F-OC-004 — shared lock release can remove a replacement holder's lock

- **Disposition:** Mechanism confirmed; shared cross-module blast radius. The replacement requires an external directory replacement between the token read and removal; no runtime interleaving was executed.
- **Evidence:** `integrations/openclaw/lib/file-lock.mjs:188-212` reads and validates the recorded owner token once. `:220-240` then unlinks the current `owner.json` and removes the directory without re-reading that token; `release` calls the two stages in sequence at `:264-270`. The module documents the replacement-holder interleaving at `:115-120`.
- **Production callers / effect:** `decision-ledger.mjs:436-438` and `queue-manager.mjs:246-259,382-383` use this lock for serialized writes; topology `lib/ledger.mjs:1503-1508` uses it for the journal writer. If holder A's lock is externally removed and holder B reacquires before A's removal, A can erase B's lock and permit a third writer inside B's critical section. Topology journal writes can then lose mutual exclusion; decision and queue files can have concurrent read-modify-write operations.
- **Common cause / related live finding:** F-433 (`docs/execution/findings.md:915-926`) is the analogous read-once/delete race in recovery drivers, not this release path. Both lack compare-at-mutation protection. The shared library is also imported by Skill Store (`zink-skill-store/src/catalog.mjs:16-29`), so changing release semantics affects Skill Store promotion serialization as well as OpenClaw decision/queue/topology writers. The file is materialized into the deployed plugin (`integrations/openclaw/lib/policy.mjs:1817-1823,1825-1830`), and asset-predecessor expectations are pinned in `tests/m11-t1-r2-file-lock-asset-predecessor.test.mjs:59-99`; a fix there has packaging/deployment compatibility blast radius in addition to runtime callers.
- **Fix-site blast radius:** A compare-and-remove repair in `file-lock.mjs` changes the shared lock protocol for decision ledger, queue, topology ledger, and Skill Store. Keep the one owner-token protocol and ensure packaged plugin asset admission/build evidence moves with the new bytes; do not implement a topology-only lock variant.

## F-OC-005 — concurrent same-ID decisions overwrite under the writer lock

- **Disposition:** Code-proven race mechanism; production reachability is latent/unestablished. Do not treat it as a demonstrated live overwrite at this tree.
- **Evidence:** `integrations/openclaw/lib/decision-ledger.mjs:579-638` refreshes and checks the instance map before it calls `save`; deterministic identity excludes decision text (`:596-607`). `save` acquires the writer lock afterward at `:436-438`, reads the durable set inside the lock at `:446-448`, and unconditionally replaces an existing ID at `:449-450`. Two processes with stale, empty maps and different decision text for the same question can therefore both return success; the second wins, contrary to `docs/contracts/decision-ledger.md:48`'s `DECISION_ID_CONFLICT` rule.
- **Production caller check:** The only production `recordDecision` invocation in `integrations/openclaw/` is `index.mjs:1671` inside exported `handleOwnerDecisionConfirmation` (`:1589-1596`); repository-wide references outside that definition are tests and documentation. The registered plugin `ASK_USER` path at `index.mjs:2630-2654` reads prior decisions but does not call `recordDecision`. Thus the writer race is not shown reachable through a current registered plugin action. Cross-process serialization is meaningful only if an external caller or multiple gateway processes share this configured store; neither is established here.
- **Common cause / relationship:** Shares the lock primitive with F-OC-004 but is a different defect: the lock correctly serializes save operations; the conflict check is outside the lock and is not repeated against the durable record. F-404 (`findings.md:668-679`) is key-order replay equality, not same-ID conflicting decisions.
- **Fix-site blast radius:** Revalidate the same-ID record under the `DecisionLedger.save` lock and refuse differing decision content with `DECISION_ID_CONFLICT`; this is scoped to the decision store and owner-confirmation writer. A shared-lock fix instead affects all callers listed under F-OC-004. If changing handler registration/reachability, preserve the plugin's owner-only gate at `index.mjs:1597-1602` and its separation of skill, Knowledgebase, and operational-state classifications at `:1613-1632`.

## F-OC-006 — duplicate ingress can create multiple tasks for one origin

- **Disposition:** Reducer invariant gap confirmed; the candidate's stated same-process production race is not confirmed and is contradicted by the synchronous ingress path. Conditional cross-process firing remains unestablished.
- **Evidence:** `integrations/openclaw/topology/lib/workflow.mjs:631-655` makes `WORKFLOW_OPENED` idempotent by `task_id` and inserts a different ID without checking uniqueness of the origin tuple. `findSession` requires exactly one session/run owner at `:323-358`; two accepted task records with the same session/run can therefore make resolution throw `EXECUTION_STATE_UNKNOWN`. Plugin ingress checks the origin binding and mints at `integrations/openclaw/plugins/zink-governance/index.mjs:9535-9555`, then appends at `:9619-9627`; ledger append reads current state and applies the event while holding the writer lock at `integrations/openclaw/topology/lib/ledger.mjs:1973-2004`.
- **Production interleaving check:** The production caller is `authenticateIngress` at `index.mjs:9399` invoked directly, without `await`, inside `beforeRun` at `:8071-8086`. For the Discord branch, the origin lookup, ID mint, duplicate check and `recordWorkflowEvent` execute synchronously on the Node event loop; there is no suspension between `:9535` and `:9626`. Same-process hook concurrency therefore cannot make both handlers observe the old snapshot in the proposed interval. Separate processes sharing one root could interleave at the precheck, but this repository does not establish a multi-gateway writer topology. The serialized reducer still permits a second origin under a different ID if such a writer exists.
- **Related findings:** F-393–F-398 and F-531 cover separate workflow outcome, state, or cancellation defects. Sequential identity coverage cited by scan-oc-4 does not establish this conditional race.
- **Fix-site blast radius:** If owner policy requires origin uniqueness irrespective of deployment topology, enforce it in the reducer under `recordWorkflowEvent`'s writer lock (`workflow.mjs:631-655`) so every event producer and replay observes the same invariant. Changing only the plugin precheck would not protect other event producers or a second process. A reducer refusal must preserve existing `WORKFLOW_OPENED` replay semantics and named error handling at plugin ingress. Until a multi-process production caller is evidenced, retain the concurrency claim as latent/conditional rather than a confirmed live production defect.

## F-OC-007 — superseded delegated run can pass specialist message provenance

- **Disposition:** Confirmed boundary defect; Medium. Production listener and allow path are present.
- **Evidence:** The registered `message_sending` hook is at `integrations/openclaw/plugins/zink-governance/index.mjs:10178-10182`; it calls `specialistExecutionProvenance` for specialist agents at `:10205-10215`. The helper resolves with `findSession(..., true)` at `:10157-10162`, receives only `delegation.agent_id` at `:10163-10175`, and the evaluator checks agent/task approval and task-wide workflow status but not the current native run at `index.mjs:876-902`. Topology explicitly matches `previous_native_run_ids` when `includePrevious` is true (`integrations/openclaw/topology/lib/workflow.mjs:323-344`), defines superseded attempts at `:421-434`, and retains the old run ID while replacing `native_run_id` on continuation at `:1961-1973`. A prior run can therefore resolve to the same delegation and active task, pass the message gate, and reach formatted Discord output (`index.mjs:10205-10215,10307-10310`).
- **State-transition distinction:** The reducer's result/callback arms do check `isSupersededAttempt` (`workflow.mjs:737,1614,1650`); the message provenance path bypasses that current-attempt condition. F-532 (`findings.md:1526-1537`) concerns the separate `execution_finished`/queue finish fence and is not this Discord message admission path.
- **Fix-site blast radius:** The current-run identity belongs to topology delegation state, while the decision to block/publicize a Discord message belongs to the governance plugin. Pass/verify the live run binding at the plugin provenance seam using topology's current-run data, and preserve `findSession` historical lookup for consumers that need history. Replacing global historical resolution with current-only lookup could break replay/forensics and other OpenClaw hooks; scope the check to specialist message authorization.
