## Existing finding cross-checks

### F-OC-002 — aggregate ZIP expansion in result validation: confirmed; scope is incomplete

- **Category / severity:** F6 — Reliability & Performance / High.
- **Affected modules:** OpenClaw artifact validation and Excel writer; governance plugin is the production caller.
- **Status:** Confirmed by static source path; no resource-exhaustion probe was run.
- **Root cause:** Both OpenClaw ZIP readers inflate untrusted entry data without an aggregate expanded-byte or entry-count budget; the Excel writer reader has no per-entry output cap either.
- **Evidence:** The result validator trusts the ZIP 16-bit central-directory count at `integrations/openclaw/lib/artifact-validator.mjs:153-168`, inflates each entry up to 25 MiB at `:191-198`, and retains buffers in `contents` at `:167,191-198`; it applies no aggregate expanded-byte or entry-count budget. The outer 25 MiB artifact ceiling at `:784-808` bounds compressed input bytes only. Distinct central-directory names can reuse a local stream because the parser reads `localOffset` but does not require unique offsets or compare the local-header name (`:173-189`).
- **Additional same-class live sink:** `integrations/openclaw/lib/excel-writer.mjs:123-174` independently parses ZIPs. It loops over the declared entry count (`:140-143`), calls `zlib.inflateRawSync(raw)` with no `maxOutputLength` at `:169-171`, and retains expanded data in a `Map` (`:142,171`). `executeExcelOperation` calls this parser through `readWorkbookSheetNames` for `load` (`:688-697`), `validate` (`:733-752`), and `populate` template reads (`:795-827`); the hosted caller supplies the sandbox at `index.mjs:4845-4864`. An untrusted or oversized workbook already in that sandbox can trigger the inflate path through governed operations, independently of result validation.
- **Concrete static reproduction:** For result validation, use many distinct central-directory names pointing to the same compressed stream and include required Excel parts; the validator inflates and retains a new buffer per distinct name, with a 25 MiB per-entry cap. For the writer, a single highly compressed workbook/template member is sufficient because its inflate has no output cap. The ZIP count field permits 65,535 entries, giving a theoretical aggregate over 1.5 TiB at 25 MiB per entry in the validator path. No crafted ZIP was created or executed.
- **Impact:** Malicious or malformed Excel ZIP input can consume excessive OpenClaw memory/CPU during result validation or Excel load/validate/populate, disrupting unrelated OpenClaw work. Writer-side parsing lacks even the validator's individual inflation bound.
- **Acceptance criteria:** Bound entry count and total expanded bytes before retaining buffers in both live readers; also impose a per-entry output ceiling in the writer reader. Regression fixtures should cover repeated stream references, many entries, a single expansion over limit, and ordinary workbooks.
- **Related findings:** Same root as `F-OC-002` and Phase 1 `CAND-oc-2-01` (`docs/execution/reports/p1/scan-oc-2.md:10-20`), not a duplicate. `F-502` is a separate publisher path. No existing register item found for the writer's unbounded template/load inflate.
- **Fix-site blast radius:** Bounding only content inflation affects Excel result validation directly; changing a shared parser/count rule also affects Power BI and DOCX ZIP callers (`artifact-validator.mjs:131-139,219-233,522-523,1139-1143,1547-1553`) plus Excel load/validate/populate and template parsing (`excel-writer.mjs:123-174,192-199,517-564`). Keep parser/resource policy in the OpenClaw hosting boundary; changing Zink Tools call schemas alone leaves both readers exposed. No Knowledgebase or Skill Store state is involved.

### F-OC-003 — dangling-symlink Excel write: sink confirmed, setup precondition qualified

- **Category / severity:** F2 — Security & Authorization / Medium.
- **Affected modules:** OpenClaw Excel writer and governance plugin; the Tool schema admits the model-selected relative path.
- **Status:** Confirmed path behavior by static inspection. This audit did not establish that the model can create the required filesystem symlink with available tools.
- **Root cause:** `realpathOf` reconstructs unresolved target paths after any `realpathSync` error, which treats an existing dangling final symlink as a nonexistent ordinary target; the later write follows the link.
- **Evidence:** `realpathOf` catches failed resolution, walks to an existing ancestor, and appends unresolved segments (`integrations/openclaw/lib/excel-writer.mjs:454-467`). For a dangling final-component symlink inside the workspace pointing outside, `assertInsideWorkspace` sees the reconstructed in-workspace path and accepts it (`:474-480`). Target validation is at `:660-673`, then `fs.writeFileSync(targetPath, buf)` follows the symlink at `:841-842`. The production Excel handler passes `resolveAgentSandboxDir("excel")` as `baseDir` (`integrations/openclaw/plugins/zink-governance/index.mjs:4845-4864`); the Tool schema admits `file_path` (`zink-tools/contracts/tools/zink-excel.schema.json:45-53`).
- **Reproduction (static):** Pre-place `<excel-sandbox>/report.xlsx` as a dangling symlink to `<existing-outside-dir>/new-report.xlsx`, then invoke governed `generate` for `report.xlsx`. Containment reconstructs the symlink path as inside the sandbox; the file write follows it and creates the outside target. The symlink must already exist and its target parent must exist. No runtime reproduction was run.
- **Impact:** Under that precondition, an approved Excel write can create workbook bytes outside the specialist sandbox. The audit found no model-call path that itself creates the required symlink, so exploit setup is environmental or pre-existing rather than an evidenced model-controlled action.
- **Acceptance criteria:** Refuse symlinked path components, including a dangling final link, before any workbook or preview write; add a regression proving the outside target and previews are not created.
- **Related findings:** Confirms `F-OC-003` and Phase 1 `CAND-oc-2-02` (`scan-oc-2.md:22-32`); these are one issue. Related to, not duplicate of, `F-563` (`findings.md:1838-1849`), whose sink is `discord-result-preview.mjs:140-169`.
- **Fix-site blast radius:** A write-target fix in `excel-writer.mjs` affects all governed generate/create/append/write/populate workbook and preview outputs; preserve ordinary new-file writes and template reads. If sharing a filesystem helper, separately preserve the Discord preview's distinct output root. Do not relax either sandbox boundary.

## Additional Tool/governance contract candidate

### CAND-xcheck-oc-artifact-01 — native Excel execution errors bypass the declared output shape

- **Category / severity:** F4 — Integration & Contract Violations / Low.
- **Legacy register id:** — (candidate for Phase 3 triage).
- **Affected modules:** OpenClaw governance plugin and Zink Tools Excel output contract.
- **Status:** Confirmed static output-shape mismatch; no caller-side failure was executed.
- **Root cause:** The shared native-tool exception wrapper serializes a generic `{status:"ERROR", tool, error, message, code}` response. The Excel output schema declares a closed shape requiring `operation` and `success`, but the plugin skips schema validation whenever status is `ERROR`.
- **Evidence:** A thrown Excel writer error reaches the shared catch at `integrations/openclaw/plugins/zink-governance/index.mjs:5292-5336`, which returns the generic object at `:5323-5335`. The Excel output schema requires `operation` and `success` and sets `additionalProperties:false` (`zink-tools/contracts/tools/zink-excel.schema.json:56-74`). `validateToolOutputEnvelope` skips the schema check when `status.toUpperCase() === "ERROR"` (`index.mjs:5400-5417`), so the registered boundary accepts this shape without checking missing required fields or extra `message`/`code` properties.
- **Reproduction:** A writer exception such as `ARTIFACT_PATH_ESCAPE` or `EXCEL_TEMPLATE_NOT_FOUND` reaches the catch, which emits the generic object without `operation`/`success`; the output validator bypasses schema validation for its `ERROR` status. Not run.
- **Acceptance criteria:** Define one declared error output shape for `zink_excel` and make the native wrapper emit it, or explicitly define and validate a shared terminal-error envelope. A regression should assert required fields and allowed properties while preserving truthful `ERROR` status.
- **Related findings:** `F-539` (`findings.md:1604-1615`) covers inconsistent error-code declarations; `F-549` (`:1695-1706`) covers error-code carriers/discriminators. This candidate is the separate closed output-schema bypass. The stale Model A versus hosted-writer prose mismatch is already `CAND-xcheck-tools-oc-02` (`xcheck-tools-oc.md:29-35`) and is not repeated.
- **Fix-site blast radius:** Changing `validateToolOutputEnvelope` or the shared catch affects all callable tools registered by this governance plugin (`index.mjs:5292-5336,5360-5367`); changing only the Excel response affects its Tool output contract and callers. Preserve downstream interpretation of `ERROR`, `BLOCKED`, `UNAVAILABLE`, and `ENGINE_NOT_IMPLEMENTED`.
